Component specs are JavaScript modules that define a component's API. Specs enable automatic attribute mapping, support for three HTML dialects, and [machine-readable documentation](/docs/api/specs/documentation).

## Why Specs Exist

**Specs are the rosetta stone for component settings.** Write one definition, and it becomes web component properties, user documentation, machine-readable specs, CSS classes, natural language descriptions, and AI-interpretable semantic mappings.

Here's what a spec looks like:

```javascript
export default {
  name: 'Button',
  variations: [
    {
      name: 'Emphasis',
      attribute: 'emphasis',
      description: 'be emphasized in a layout',
      options: [
        { name: 'Primary', value: 'primary' },
        { name: 'Secondary', value: 'secondary' }
      ]
    }
  ]
}
```

This single definition translates into multiple forms:

1. **It becomes HTML attributes.** The human concept "emphasized" becomes the attribute `emphasis`, and the option name "Primary" becomes the value `primary`. This attribute mapping enables developers to write `<ui-button primary>` as shorthand, working in [three dialects](/docs/api/specs/parsing):

```html
<ui-button primary>Save</ui-button>
<ui-button emphasis="primary">Save</ui-button>
<ui-button class="primary">Save</ui-button>
```

2. **It becomes CSS classes.** The template provides a [&#123;ui&#125; variable](#the-ui-css-class-string) in the data context to add related class names anywhere in your component shadow DOM. When you write `<ui-button primary>`, the runtime automatically includes `"primary"` in the &#123;ui&#125; string.

3. **It becomes documentation.** The [Button primitive docs](/ui/primitives/button#variations) use [`getDefinition()`](/docs/api/specs/documentation#getdefinition) to add a code example under the [Variations](/ui/primitives/button#emphasis-example) heading, showing live `<ui-button primary>` and `<ui-button secondary>` examples with the description "A button can be emphasized in a layout."

4. **It becomes runtime metadata.** [`getWebComponentSpec()`](/docs/api/specs/spec-reader#getwebcomponentspec) maps variations of a concept and specific instances to their attributes and classes. For example, an icon spec with hundreds of icon options generates `optionAttributes: { 'left-arrow': 'icon', 'right-arrow': 'icon', ... }`, enabling `<ui-icon left-arrow>` to map to `icon="left-arrow"` with class `"left-arrow"` applied.

5. **It becomes natural language.** The code `<ui-button primary>` becomes the human-readable description **"A button can be emphasized in a layout"** in generated documentation—translating HTML into natural language explanations for users.

6. **It enables AI interpretation.** Metadata like `usageLevel` and natural language descriptions provide a translation layer from human intent to implementation. An AI can translate "emphasize this button more" by matching "emphasize" to the `emphasis` attribute, checking `usageLevel: 1` to confirm it's commonly used, reading the description "be emphasized in a layout", and suggesting `<ui-button primary>` as the implementation.

Change `primary` to `main` in your spec, and all six representations update automatically. No manual synchronization across documentation, CSS logic, validation rules, or AI interpretation.

## How Specs Work

Specs are machine-readable API definitions that transform into runtime metadata.

**Without a spec**, components only support verbose attributes:

```javascript
defineComponent({
  tagName: 'ui-button',
  defaultSettings: {
    primary: false,
    size: 'medium',
  },
});
```

```html
<!-- Only this syntax works -->
<ui-button primary="true" size="large">Save</ui-button>
```

**With a spec**, you define your component's API once:

```javascript
import componentSpec from './specs/button.component.js';

defineComponent({
  tagName: 'ui-button',
  componentSpec,  // Generated by SpecReader.getWebComponentSpec()
  template,
  css,
});
```

And get multiple benefits automatically:

```html
<!-- Three HTML dialects work automatically -->
<ui-button primary large>Save</ui-button>
<ui-button emphasis="primary" size="large">Save</ui-button>
<ui-button class="primary large">Save</ui-button>
```

Specs also provide:
- Automatic CSS class generation from attributes
- Bidirectional attribute-to-property mapping
- [Auto-generated documentation](/docs/api/specs/documentation) from your spec definitions
- Runtime validation of allowed attribute values

> [!info]
> **Specs in production:** Every page in [UI Primitives](/ui/primitives/button) is auto-generated from specs using [`SpecReader`](/docs/api/specs/spec-reader). The types, states, and variations you see documented are read directly from `.spec.js` files—not manually written.

> [!info]
> Specs are optional. Use `defaultSettings` and `defaultState` for simple components. Use specs when building design systems or components with many configurable options.

## Spec Format

Specs are JavaScript modules that export pure data. They must be JSON-serializable.

### Simple Spec

Most specs are plain objects with template literals:

```javascript
// divider.spec.js
export default {
  uiType: 'element',
  name: 'Divider',
  description: 'visually segment content into groups',
  tagName: 'ui-divider',
  exportName: 'UIDivider',

  content: [
    {
      name: 'Text',
      attribute: 'text',
      description: 'include centered text',
      exampleCode: `<ui-divider text="Or"></ui-divider>`,
    },
  ],

  types: [],
  states: [],
  variations: [],
  settings: [],
  events: [],
};
```

### Using Spec Helpers

Import common variations to avoid repetition:

```javascript
// label.spec.js
import { SIZE_VARIATION } from '@semantic-ui/specs';

export default {
  name: 'Label',
  tagName: 'ui-label',
  exportName: 'UILabel',

  variations: [
    {
      name: 'Badge',
      attribute: 'badge',
      description: 'be used as a badge',
    },
    SIZE_VARIATION,  // Includes all 8 size options
  ],
};
```

### Using Helpers

For complex specs, use [helper functions](/docs/api/specs/shared-terms):

```javascript
// button.spec.js
import {
  COLOR_OPTIONS,
  getStates,
  getVariations,
} from '@semantic-ui/specs';

export default {
  name: 'Button',
  tagName: 'ui-button',

  states: getStates(['hover', 'active', 'disabled', 'loading']),

  variations: [
    ...getVariations(['floated', 'fluid', 'compact', 'size']),
    {
      name: 'Colored',
      attribute: 'color',
      description: 'be colored',
      options: COLOR_OPTIONS,
    },
  ],
};
```

## Spec Sections

Every spec has these top-level fields:

```javascript
{
  uiType: 'element',           // Always "element"
  name: 'Button',              // Display name
  description: 'trigger actions',  // What it does
  tagName: 'ui-button',        // HTML tag
  exportName: 'UIButton',      // JavaScript export

  content: [],      // Slots and content areas
  types: [],        // Mutually exclusive behaviors
  states: [],       // Runtime state changes
  variations: [],   // Stackable visual modifications
  settings: [],     // Configuration properties
  events: [],       // Custom events
}
```

### Content

Define slots and content areas:

```javascript
content: [
  {
    name: 'Icon',
    attribute: 'icon',
    slot: 'icon',
    description: 'include an icon',
    exampleCode: `<ui-button icon="save">Save</ui-button>`,
  },
],
```

### Types

Define mutually exclusive behaviors:

```javascript
types: [
  {
    name: 'Emphasis',
    attribute: 'emphasis',
    description: 'be emphasized in a layout',
    options: [
      {
        name: 'Primary',
        value: 'primary',
        description: 'be emphasized as the first action',
      },
      {
        name: 'Secondary',
        value: 'secondary',
        description: 'be emphasized as a secondary option',
      },
    ],
  },
],
```

### States

Define runtime state changes:

```javascript
states: [
  {
    name: 'Disabled',
    attribute: 'disabled',
    description: 'have interactions disabled',
  },
],
```

### Variations

Define stackable visual modifications:

```javascript
variations: [
  {
    name: 'Size',
    attribute: 'size',
    description: 'vary in size',
    options: [
      { name: 'Small', value: 'small' },
      { name: 'Large', value: 'large' },
    ],
  },
  {
    name: 'Fluid',
    attribute: 'fluid',
    description: 'take the width of its container',
  },
],
```

### Settings

Define configuration properties:

```javascript
settings: [
  {
    name: 'Href',
    type: 'string',
    attribute: 'href',
    description: 'link to a webpage',
  },
  {
    name: 'Debounced',
    type: 'boolean',
    attribute: 'debounced',
    defaultValue: false,
    description: 'debounce input value changes',
  },
],
```

### Events

Define custom events:

```javascript
events: [
  {
    eventName: 'change',
    description: 'occurs after the value changes',
    arguments: [
      {
        name: 'value',
        description: 'the updated value',
      },
    ],
  },
],
```

## Types vs Variations

Types represent distinct categories. Variations stack.

```html
<!-- Types: generally one at a time -->
<ui-button primary>Save</ui-button>
<ui-button secondary>Cancel</ui-button>

<!-- Variations: combine many -->
<ui-button large fluid red>Delete</ui-button>
```

This is a linguistic convention, not enforcement. The system doesn't prevent combinations. Types vs variations guide how humans think about attributes.

## Spec Helpers

The [`@semantic-ui/specs`](/docs/api/specs/shared-terms) package provides reusable constants and helpers.

### Using Helpers

Get multiple variations with [`getVariations()`](/docs/api/specs/shared-terms#getvariations):

```javascript
import { getVariations } from '@semantic-ui/specs';

export default {
  variations: [
    ...getVariations(['size', 'colored', 'fluid', 'compact']),
    // Add custom variations
  ],
};
```

Get multiple states with [`getStates()`](/docs/api/specs/shared-terms#getstates):

```javascript
import { getStates } from '@semantic-ui/specs';

export default {
  states: getStates(['hover', 'focus', 'active', 'disabled', 'loading']),
};
```

### Advanced Cases

Import individual [constants](/docs/api/specs/shared-terms#variation-constants) to modify with [`modifyVariation()`](/docs/api/specs/shared-terms#modifyvariation):

```javascript
import { SIZE_VARIATION, modifyVariation } from '@semantic-ui/specs';

variations: [
  modifyVariation(SIZE_VARIATION, {
    usageLevel: 3,
  }),
]
```

Import [options arrays](/docs/api/specs/shared-terms#options-arrays) for different attribute names:

```javascript
import { COLOR_OPTIONS } from '@semantic-ui/specs';

export default {
  variations: [
    {
      name: 'Tint',
      attribute: 'tint',
      options: COLOR_OPTIONS,
    },
  ],
};
```

## Converting Specs to Component Specs

Specs must be converted to component specs for use with `defineComponent` using [`SpecReader`](/docs/api/specs/spec-reader). You can do this at build time or runtime.

### Build Time (Recommended)

Convert specs during your build for tree-shaking and smaller bundles:

```javascript
import { SpecReader } from '@semantic-ui/specs';
import buttonSpec from './button.spec.js';

const reader = new SpecReader(buttonSpec);
const componentSpec = reader.getWebComponentSpec();

// Write componentSpec to a file or use in your build
```

See [`getWebComponentSpec()`](/docs/api/specs/spec-reader#getwebcomponentspec) for details.

### Runtime

Convert specs when your component loads:

```javascript
import { SpecReader } from '@semantic-ui/specs';
import buttonSpec from './button.spec.js';

const reader = new SpecReader(buttonSpec);
const componentSpec = reader.getWebComponentSpec();

defineComponent({
  tagName: 'ui-button',
  componentSpec,
  template,
  css,
});
```

> [!warning]
> Runtime conversion means the full spec and SpecReader are included in your bundle. Use build-time conversion for production.

The component spec contains optimized runtime metadata:

```javascript
{
  tagName: 'ui-button',
  attributes: ['icon', 'emphasis', 'size'],
  optionAttributes: {
    'primary': 'emphasis',
    'secondary': 'emphasis',
    'large': 'size',
  },
  propertyTypes: {
    'emphasis': 'string',
    'disabled': 'boolean',
  },
  allowedValues: {
    'emphasis': ['primary', 'secondary'],
    'size': ['mini', 'tiny', 'small', 'large', 'huge', 'massive'],
  },
  attributeClasses: ['icon', 'disabled'],
  defaultValues: {
    'iconOnly': false,
  }
}
```

## How Specs Work at Runtime

Specs are transformed into runtime metadata that powers your component's template data and styling.

### Spec Attributes Become Settings

When you define attributes in your spec, they become reactive settings available in templates and lifecycle callbacks:

```javascript
// In your spec
variations: [
  {
    name: 'Emphasis',
    attribute: 'emphasis',
    options: [
      { name: 'Primary', value: 'primary' },
      { name: 'Secondary', value: 'secondary' },
    ],
  },
]
```

```html
<!-- In your HTML -->
<ui-button primary large>Save</ui-button>
```

```sui
<!-- In your template -->
<button class="ui button &#123;ui&#125;">
  Current emphasis: &#123;emphasis&#125;
  Current size: &#123;size&#125;
</button>
```

The spec's `optionAttributes` maps `primary` → `emphasis="primary"`, making the attribute available as <code>{'&#123;emphasis&#125;'}</code> in templates.

### The &#123;ui&#125; CSS Class String

Spec attributes automatically generate CSS classes through the <code>{'&#123;ui&#125;'}</code> variable:

```sui
<div class="ui button &#123;ui&#125;">
  <!-- &#123;ui&#125; becomes "primary large" -->
</div>
```

The transformation rules:
- **Option values**: `emphasis="primary"` → class `"primary"`
- **Boolean attributes**: `disabled` → class `"disabled"`
- **Attribute classes**: `icon="save"` → class `"icon"` (if in spec's attributeClasses)

### Accessing Settings in Lifecycle

Settings are available as destructured arguments in all [lifecycle callbacks](/docs/guides/components/lifecycle):

```javascript
defineComponent({
  tagName: 'ui-badge',
  componentSpec,

  createComponent: ({ settings }) => ({
    setStatus(newStatus) {
      settings.status = newStatus;  // Updates setting and triggers re-render
    },

    getCurrentStatus() {
      return settings.status;
    },
  }),

  onCreated: ({ settings, el }) => {
    console.log('Initial status:', settings.status);
  },
});
```

### Complete Data Flow

```
HTML Attribute
  <ui-button primary large>
      ↓
optionAttributes mapping
  { 'primary': 'emphasis', 'large': 'size' }
      ↓
Element Properties
  el.emphasis = 'primary'
  el.size = 'large'
      ↓
Template Data Context
  &#123;emphasis&#125; = "primary"
  &#123;size&#125; = "large"
  &#123;ui&#125; = "primary large "
```

## Writing Style

### Descriptions

Use imperative mood without the component name:

```javascript
// Good
description: 'be emphasized'
description: 'appear small'
description: 'have interactions disabled'

// Bad
description: 'The button can be emphasized'
description: 'Makes the button appear small'
```

The [`formatDescription()`](/docs/api/specs/utilities#formatdescription) utility automatically prepends "A button can" or "An icon can".

### Template Literals

Use template literals for HTML examples:

```javascript
// Single example
exampleCode: `<ui-button icon="pause">Pause</ui-button>`

// Multiline
exampleCode: `
  <ui-button primary>Confirm</ui-button>
  <ui-button>Cancel</ui-button>
`

// Multiple examples (array)
exampleCode: [
  `<ui-button>Example 1</ui-button>`,
  `<ui-button>Example 2</ui-button>`,
]
```

### Usage Levels

Indicate feature commonality (1-5):

```javascript
{
  name: 'Size',
  usageLevel: 1,  // Essential
  description: 'vary in size',
}

{
  name: 'Animated',
  usageLevel: 3,  // Advanced
  description: 'animate to show hidden content',
}
```

Scale: 1 = Essential, 2 = Common, 3 = Advanced, 4 = Specialized, 5 = Rare

## When to Use Specs

**Use specs when:**
- You need all three HTML dialects
- Building a design system or component library
- You want AI assistants to understand your components
- Creating components with many attribute options
- Building plural components with shared variations

**Skip specs when:**
- Building one-off internal components
- Prototyping with rapidly evolving APIs
- Simple components where overhead isn't justified
- Components only need a few settings

Specs are human communication tools. They describe patterns and enable tooling, but don't enforce rigid rules. Like natural language, they're strictly fuzzy.
