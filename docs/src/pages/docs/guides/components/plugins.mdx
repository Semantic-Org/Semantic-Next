Plugins extend `defineComponent` with custom configuration options, callback parameters, and template helpers across your application.

> See the [Component Plugins API Reference](/docs/api/component/plugins) for method signatures and options.

## Using Plugins

### Adding a Plugin

Call `addPlugin` once at startup to enable a plugin and configure its application-wide settings.

```javascript {5-8}
import { addPlugin } from '@semantic-ui/component';
import { I18n } from './i18n-plugin.js';
import { strings } from './locales.js';

addPlugin(I18n, {
  locale: 'en',
  strings,
});
```

### Configuring Components

Once installed, the plugin's `namespace` becomes a top-level option on `defineComponent`, and its helpers and callback parameters are available inside the component.

```javascript {3-4,6}
defineComponent({
  tagName: 'checkout-summary',
  i18n: 'checkout',
  template: `<h3>{t 'title'}</h3>`,
  events: {
    'click ui-button'({ i18n, data }) {
      i18n.setLocale(data.locale);
    },
  },
});
```

Active plugins also attach their instance to the DOM element at `el[namespace]` (`document.querySelector('checkout-summary').i18n.setLocale('es')`).

## Extending Callbacks

### Shared Parameters

Use `extendParams` to add shared utilities or services directly to the destructured `{ ... }` callback arguments received by every component (`createComponent`, `events`, `keys`, and lifecycle hooks).

```javascript {4-6}
import { extendParams } from '@semantic-ui/component';

extendParams({
  setCurrency: (code) => currency.set(code),
  formatPrice: (usd) => format(usd, currency.get()),
});
```

### Per-Instance Parameters

Pass a function when the injected helper needs access to the component's own callback arguments, such as `el` or `state`.

```javascript {1-3}
extendParams(({ el }) => ({
  track: (event, data) => analytics.send(el?.tagName, event, data),
}));
```

## Authoring Plugins

### Custom Component Options

`registerPlugin` lets you define a new top-level option on `defineComponent`. Setting `appliesTo: 'configured'` runs the plugin only on components that pass that option (`config`):

```javascript {3}
defineComponent({
  tagName: 'sticky-note',
  persist: ['note'],
  defaultState: { note: '' },
});
```

### Instance Helpers & Params

To expose per-component methods, return them from `createPlugin`, then map them into callbacks with `lifecycleParams` and into templates with `templateHelpers`.

```javascript {3-9,11-16}
export const I18n = registerPlugin({
  namespace: 'i18n',
  createPlugin({ settings }) {
    return {
      t(key) {
        const { locale, prefix, strings } = settings;
        const path = prefix ? `${prefix}.${key}` : key;
        return get(strings[locale], path) ?? key;
      },
    };
  },
  lifecycleParams({ self }) {
    return { t: self.t, i18n: self };
  },
  templateHelpers({ self }) {
    return { t: self.t };
  },
});
```

Because `templateHelpers` is a function here, `{t 'title'}` is scoped to each component instance and automatically resolves that component's `prefix`.

### Reactive Settings

`defaultSettings` merged in `addPlugin` are wrapped in a reactive proxy, while `resolveSettings` maps shorthand component config (like `i18n: 'checkout'`) onto that component's settings.

```javascript {2-6,7-12}
export const I18n = registerPlugin({
  namespace: 'i18n',
  defaultSettings: {
    locale: 'en',
    strings: {},
    prefix: '',
  },
  resolveSettings({ settings, config }) {
    if (isString(config)) {
      return { ...settings, prefix: config };
    }
    return settings;
  },
});
```

Keys overridden by a component (`prefix: 'checkout'`) stay local to that component, while unoverridden keys (`locale`) read and write through to the shared plugin settings across the page.
