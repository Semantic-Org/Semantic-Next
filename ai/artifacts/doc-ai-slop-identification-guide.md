# AI Slop Identification & Removal Guide

## Core Principle
**Remove problems without adding new ones.** It's better to delete 3 issues than to rewrite and introduce 2 new problems.

## Good Writing Reference
See `doc-good-writing-examples.md` for concrete examples of excellent technical writing patterns to emulate. Key principles:
- 1-2 sentence paragraphs
- Direct statements without hedging
- No introductory fluff
- Code examples immediately after brief explanations
- No concluding summaries

## Identification Patterns

### 1. Concluding Paragraphs
**Pattern**: Final paragraphs that restate obvious benefits using marketing language.
**Example**: "By working with this AST structure, you can create highly optimized and flexible rendering systems that suit your specific needs while leveraging the powerful parsing capabilities of the Semantic UI Templating system."
**Fix**: Delete entirely. The benefits are self-evident from the content.

### 2. Self-Referential Terminology
**Pattern**: Overly formal references to the project itself.
**Bad**: "Semantic UI Templating system", "Semantic UI framework's powerful features"
**Good**: "templates", "framework features"
**Fix**: Simplify references. The reader knows they're reading Semantic UI docs.

### 3. Hedging Words
**Pattern**: Unnecessary qualifiers that weaken clarity.
**Examples**: "various", "specific", "certain", "particular", "serves several purposes", "hypothetically"
**Fix**: Delete the qualifier or make the statement direct.

### 4. Marketing Buzzwords
**Pattern**: Adjectives that add no technical value.
**Examples**: "powerful", "flexible", "robust", "highly optimized", "seamless", "comprehensive"
**Fix**: Delete the adjective. Let features speak for themselves.

### 5. Passive Voice
**Pattern**: Passive constructions where active voice is clearer.
**Bad**: "An AST is generated by the TemplateCompiler"
**Good**: "The TemplateCompiler generates an AST"
**Fix**: Identify the actor and make it the subject.

### 6. Redundant Explanations
**Pattern**: Saying the same thing multiple ways.
**Example**: "The AST consists of various node types, each representing a specific element or control structure in the template. Below are the main types of nodes you'll encounter in the AST:"
**Fix**: "The AST contains these node types:"

### 7. Academic Tone
**Pattern**: Unnecessarily formal language in technical docs.
**Bad**: "This intermediate representation serves several purposes"
**Good**: "The AST lets you:"
**Fix**: Use direct, conversational technical writing.

### 8. Verbose Introductions
**Pattern**: Long setup before getting to the point.
**Bad**: "In this section, we will explore the various ways in which..."
**Good**: Just start with the content.
**Fix**: Delete the introduction, jump straight to the information.

### 9. "Note that..." Constructions
**Pattern**: Indirect way of stating facts.
**Bad**: "Note that the compiler will process..."
**Good**: "The compiler processes..."
**Fix**: Remove "Note that" and state directly.

### 10. Explaining What's Coming
**Pattern**: Telling readers what you're about to tell them.
**Bad**: "Below are the main types of nodes you'll encounter in the AST:"
**Good**: Just list the nodes.
**Fix**: Delete the preview sentence.

### 11. Missing Practical Warnings
**Pattern**: Not warning about common pitfalls or security issues.
**Bad**: Explaining a feature without mentioning gotchas.
**Good**: Clear WARNING or SECURITY NOTES sections.
**Fix**: Add warnings only if critical; don't manufacture concerns.

### 12. Lack of Do/Don't Examples
**Pattern**: Explaining concepts without showing wrong vs right approaches.
**Bad**: Long explanations of best practices.
**Good**: "Instead of this... ...do this" with code examples.
**Fix**: If the pattern exists, simplify to code comparison.

### 13. Complex Info Without Tables
**Pattern**: Explaining multi-dimensional relationships in prose.
**Bad**: "When X is Y and A is B, then C happens, unless..."
**Good**: Use a table to show relationships clearly.
**Fix**: Convert to table if truly complex; otherwise simplify.

### 14. Missing "When Not to Use" Guidance
**Pattern**: Only explaining how to use something, not when to avoid it.
**Bad**: Feature documentation without boundaries.
**Good**: Clear "When not to use X" section with alternatives.
**Fix**: Only add if there are genuine anti-patterns to avoid.

### 15. Overly Long Headers
**Pattern**: Headers that wrap in the InPageMenu sidebar.
**Character Limits**: 
- **Top-level headers**: Under 30 characters
- **Sub-headers**: Under 35 characters
**Bad**: "Understanding the Complete Lifecycle of Component Initialization" (64 chars)
**Good**: "Component Lifecycle" (18 chars)
**Fix**: Shorten to essential keywords users scan for.

### 16. Poor InPage Menu Structure
**Pattern**: Header hierarchy that creates illogical or confusing navigation groups.

### 17. Logical Inconsistencies
**Pattern**: Statements that contradict themselves or defy basic logic.
**Examples**: 
- "Outside Component" containing "Inside your component"
- "This is required" followed by "This is optional"
- "Always use X" then "Never use X"
**Fix**: Flag with user as "I see you said (X), did you mean (Y)?" and ask for clarification.

**How Rail Menu Logic Works:**
1. **If first heading is H3+**: Auto-inject page title as H2 parent for consecutive H3+ headings at start
2. **Always show two consecutive levels**: Find lowest heading level, use it as groups, next level as sub-items
3. **Groups get expand/collapse**: Main level headings become collapsible sections
4. **Sub-items show under groups**: One level deeper headings nest under their parent

**Test Your Headers**: Simulate the rail menu:
- What will be the main groups? (collapsible sections)
- What will be the sub-items under each group?
- Can users scan and find key concepts quickly?

**Bad Example**:
```
### Overview  
## Installation
### Features (orphaned - no H2 parent, no H3 siblings)
### Step 1
```
**Result**: "Installation" group only has orphaned H3s with no logical relationship

**Good Example**:
```
### Overview (page title "API Reference" auto-injected as parent)
### Features (under "API Reference")
## Installation (second main group)
### Step 1 (under Installation)
```
**Result**: "API Reference" and "Installation" as main groups with proper sub-items

## Removal Strategy

### 1. Minimal Edits
- Prefer deletion over rewriting
- If you must edit, change only the problematic words
- Maintain existing structure and flow

### 2. Consistency First
- Match the tone of well-written sections
- Use existing terminology from the codebase
- Follow established heading patterns

### 3. Quick Fixes Priority
1. Delete concluding paragraphs
2. Remove adjectives (powerful, flexible, etc.)
3. Simplify self-references
4. Cut hedging words
5. Fix obvious typos

### 4. Preserve Technical Accuracy
- Never remove technical details
- Keep all code examples
- Maintain API documentation completeness

## What NOT to Do

1. **Don't rewrite entire sections** - This introduces new problems
2. **Don't add explanations** - If it wasn't clear before, flag it for human review
3. **Don't change technical meaning** - Only fix language, not content
4. **Don't add your own style** - Match what exists

## Post-Edit Validation

After editing any page, simulate and validate the InPageMenu:

### 1. Simulate Rail Menu Output
Apply the rail menu logic to your headers:
- **Step 1**: Find first heading level (H2, H3, etc.)
- **Step 2**: If first is H3+, inject page title as parent for consecutive H3+ headings
- **Step 3**: Find lowest remaining heading level = main groups
- **Step 4**: Next level deeper = sub-items under groups

### 2. Validate Result
- **Character Count**: Top-level headers <30 chars, sub-headers <35 chars
- **Scannable Groups**: Can users quickly find main concepts in group names?
- **Logical Nesting**: Do sub-items relate to their parent group?
- **Complete Coverage**: Are all important concepts represented in the menu?

### Example Simulation:
**Input Headers:**
```
### Overview
### Quick Start  
## API Reference
### Methods
### Properties
## Examples
```

**Rail Menu Output:**
- **Page Title** (auto-injected)
  - Overview
  - Quick Start
- **API Reference** 
  - Methods
  - Properties
- **Examples** (no sub-items)

## Decision Framework

When you find problematic text, ask:
1. Can I just delete this? (Best option)
2. Can I remove just the problematic words? (Good option)
3. Do I need to restructure? (Flag for human review)
4. After changes, does the InPageMenu structure work well?

Remember: **Less is more.** Every edit risks introducing new slop.
