# Writing Documentation

> **Skill:** `docs-writing`
> **Purpose:** Prose quality standards for all documentation — baseline voice, persuasive writing for gateway pages, and editing strategy

---

## Two Writing Modes

Semantic UI docs span ~120 pages across two distinct writing modes:

| Mode | Pages | Voice | When |
|------|-------|-------|------|
| **Reference** | ~106 guides, API docs, lessons | Concise, direct, code-forward | Teaching how to use something |
| **Persuasive** | ~14 gateway/index pages | Problem-first, instability-driven | Earning attention from uncommitted readers |

Reference is the default. Most pages assume the reader has already decided to learn — respect their time. Persuasive mode applies only to gateway pages where readers are deciding whether to care.

---

## Reference Voice

The baseline for all SUI documentation. Modeled after Vite, Svelte, and Astro — direct, technical, respectful of the reader's time.

### Principles

1. **Sentence length**: Most under 20 words
2. **Paragraph length**: 1-3 sentences max
3. **Code-to-text ratio**: More code, less explanation
4. **Direct voice**: "The compiler generates an AST" not "An AST is generated by the compiler"
5. **No transitions**: Don't connect sections with "Now let's..." or "Next we'll..."
6. **Factual tone**: State what it does, not why it's great
7. **No preamble**: Don't tell readers what you're about to tell them — just tell them
8. **No conclusions**: The content ends when the information ends

### The Model: Vite Docs

**One-sentence introductions:**
> Vite (French word for "quick", pronounced /vit/, like "veet") is a build tool that aims to provide a faster and leaner development experience for modern web projects.

**Brief setup, then structure:**
> It consists of two major parts:
> - A dev server that provides rich feature enhancements over native ES modules
> - A build command that bundles your code with Rollup

**Type signatures first, examples immediately after** — no explanation between:
```
async function createServer(inlineConfig?: InlineConfig): Promise<ViteDevServer>
```

**One concept per heading, no preamble:**
> ### Browser Support
> During development, Vite assumes a modern browser is used.

### In Practice

❌ "The Abstract Syntax Tree (AST) is a powerful and flexible representation of your template that is utilized by the rendering pipeline to generate your component efficiently."

✅ "The AST represents your template structure for the rendering pipeline."

❌ "In the following section, we will explore the various node types that make up the AST structure."

✅ Just use the heading: `## AST Node Types`

❌ "It's worth noting that the template compiler provides several important capabilities."

✅ "The template compiler can:"

### Self-Referential Language

Simplify references to the project:

- ❌ "Semantic UI Templating system", "Semantic UI framework's powerful features"
- ✅ "templates", "framework features"

The reader knows they're reading Semantic UI docs.

## Persuasive Voice

For gateway/index pages, homepage, and "why semantic" content — the ~10% of pages where readers are uncommitted and pattern-matching against React/Vue/Svelte. See `docs-page-gateway` for the specific page structure (convince/excite format, templates, checklists).

### The Core Reframe

Writing changes readers' ideas. It doesn't communicate yours. Most documentation fails not because it's unclear, but because it's useless — it doesn't change anything for the reader.

### Problem-First Structure

Readers scan for tension — problems, contradictions, things that don't fit. Stability language ("building on," "grounded in," "Features include...") signals "nothing to see here."

1. **Open with a problem** the reader already feels
2. **Establish instability** — what's wrong or surprising about the status quo
3. **Show cost** — why should they care
4. **Position your content as the solution**

❌ Background → definitions → thesis → examples → conclusion
✅ Problem → tension → solution → examples

For SUI specifically, the foundational instability is: "Web components are the right standard **but** vanilla implementations force painful trade-offs in developer experience."

### Instability Language

Get to "but" or "however" within the first paragraph. If your opening paragraphs lack tension markers, readers cannot locate value.

| Function | Language |
|----------|----------|
| **Tension** | but, however, although, yet, despite, inconsistent, challenges |
| **Cost** | painful trade-offs, verbose boilerplate, forces developers to, breaks, awkward, tedious |
| **Solution** | resolves, replaces X with Y, eliminates the need for, without requiring |

### Argue, Don't Explain

Explanation reveals the inside of your head. Argument anticipates what readers will doubt.

- ❌ "Why do I think this?" (explaining)
- ✅ "Why should *they* think this?" (arguing)

You cannot explain your way to value. If readers don't perceive a problem, your explanation has no anchor.

### Writing Process ≠ Reading Process

What you discover at the end of your writing process often belongs at the beginning of the final text. The structure that helped you think is usually wrong for helping readers read.

## AI Anti-Patterns

AI-generated prose has identifiable structural tics. A single occurrence might be fine — the problem is when multiple patterns cluster or one pattern repeats throughout a piece.

### Patterns to Watch For

| Pattern | Example | Fix |
|---------|---------|-----|
| Marketing adjectives | "powerful", "flexible", "robust", "seamless" | Delete the adjective |
| Hedging words | "various", "specific", "certain", "particular" | Delete or be specific |
| "Serves as" dodge | "serves as", "stands as", "represents" | Use "is" |
| Negative parallelism | "It's not X — it's Y" | Rewrite directly |
| Rhetorical self-answer | "The result? Devastating." | State the point directly |
| Em-dash addiction | Three+ em dashes per paragraph | Commas or separate sentences |
| Bold-first bullets | "**Security**: Environment-based..." | Remove bold formatting |
| Fractal summaries | Intro + section summaries + conclusion | Delete all but the content |
| "Let's break this down" | "Let's unpack...", "Let's dive in" | Delete, just start |
| Concluding paragraphs | Final paragraph restating obvious benefits | Delete entirely |
| Short punchy fragments | "He published this. Openly. In a book." | Write real sentences |
| Grandiose stakes | "fundamentally reshape", "define the next era" | State actual impact |
| Tricolon abuse | Three parallel constructions back-to-back | Vary sentence structure |
| Historical analogy stacking | "Apple didn't... Facebook didn't..." | One example, if needed |

## Editing Existing Prose

### Pre-Edit Verification

Before modifying documentation, verify your edits won't break technical accuracy:

1. **Technical terminology** — Words like "directly," "systematically" may describe implementation behavior, not marketing. When uncertain, flag rather than delete.

2. **API behavior** — If modifying statements about reactivity, state, or data flow, verify with the user first. Never invert boolean technical statements without explicit approval. (A previous agent changed "settings are reactive" to "settings are not reactive.")

3. **Logic preservation** — After editing, scan for accidental meaning inversions. Does the edited content maintain the original technical assertions?

4. **Context evaluation** — If a word looks like marketing fluff, check whether it serves technical precision in this context. When in doubt, preserve and flag.

### Removal Strategy

**Delete over rewrite.** Removing 3 problems beats rewriting and introducing 2 new ones.

Priority order:
1. Delete concluding paragraphs
2. Remove marketing adjectives (powerful, flexible, robust, seamless)
3. Simplify self-references
4. Cut hedging words
5. Fix passive voice to active

**Do not:**
- Rewrite entire sections — this introduces new problems
- Add explanations — flag unclear content for human review
- Change technical meaning — fix language, not content
- Add your own style — match what exists

### Decision Framework

When you find problematic text:
1. Can I just delete this? → **Best option**
2. Can I remove just the problematic words? → **Good option**
3. Do I need to restructure? → **Flag for human review**

## Quick Reference

### Before Writing
- Who is the reader? Already committed (→ reference voice) or browsing (→ persuasive voice)?
- What page type? Load the relevant page-type skill.

### While Writing (Reference)
- 1-3 sentence paragraphs, most sentences under 20 words
- More code than prose
- No transitions, no introductions, no conclusions

### While Writing (Persuasive)
- Open with the problem, not background
- Get to "but" / "however" in the first paragraph
- Position features as solutions to stated problems

### While Editing
- Verify technical accuracy before changing anything
- Delete over rewrite
- Load `docs-ai-tropes` for the full anti-pattern catalog
- Match the tone of well-written sections
