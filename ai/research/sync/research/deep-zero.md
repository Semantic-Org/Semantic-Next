## 2. Architecture

**Storage.** Client: Replicache lineage — an IndexedDB-persisted B-tree/DAG commit store (`packages/replicache/src`) with in-memory IVM `MemorySource`s per table hydrated from it (`packages/zero-client/src/client/ivm-branch.ts`). Synced data persists across sessions ("If you do nothing, the synced data will be left on the device. The next login will be a little faster" — [auth docs, Logging Out](https://zero.rocicorp.dev/docs/auth)). Server: `zero-cache` maintains a **SQLite replica of Postgres** via logical replication, plus two more Postgres databases of operational state: `ZERO_CVR_DB` ("storing client view records") and `ZERO_CHANGE_DB` (recent replication log). ([self-host](https://zero.rocicorp.dev/docs/self-host))

**Topology.** zero-cache splits into one **replication-manager** (owns the replication slot, backs up the replica via litestream) and N horizontally-scaled **view-syncers** (serve client websockets, run IVM, manage CVRs, restore replica from backup). ([self-host](https://zero.rocicorp.dev/docs/self-host))

**Transport.** WebSocket. Downstream "pokes" are bracketed multi-part frames — `poke-start { baseCookie, cookie }` → N `poke-part` → `poke-end` — "The merged poke-parts can now be applied as a whole to update from baseCookie to cookie" (`packages/zero-protocol/src/poke.ts`). This is the checkpoint-bracket atomic-apply pattern ws-protocol.md §2 already cites as lineage ("Zero's pokeEnd... collapsed into one frame").

**Partial sync.** Query-driven. A *synced query* is a named function returning a ZQL expression, registered in a central `queries.ts`, deduped by hash of (name, args) in the client's `QueryManager` (`packages/zero-client/src/client/query-manager.ts` — `hashOfNameAndArgs`). The client sends its desired-query set at connect (`initConnection { desiredQueriesPatch }`, `packages/zero-protocol/src/connect.ts`) and diffs it live. zero-cache resolves each query by **calling your application server's query endpoint** (`ZERO_QUERY_URL`) which returns a ZQL AST — permissions enter by the server returning a more-restrictive query. ([queries](https://zero.rocicorp.dev/docs/queries))

**Conflict/write path.** Named *custom mutators*, dual-registered: "A copy of each mutator exists on both the client and on your server... the implementations don't have to be the same, or even compute the same result." Client applies optimistically against local IVM, push goes to **your** mutate endpoint (`ZERO_MUTATE_URL`) which runs the server implementation in a DB transaction. Rebase: "Any pending mutations which have been applied to the server have their local effects rolled back" and remaining pending mutators replay — `rebaseMutation` re-runs the mutator implementation against a new basis commit, with strictly sequential per-client `mutationID` enforced (`packages/replicache/src/db/rebase.ts` throws "Inconsistent mutation ID" on gaps). Removed mutator names get a no-op stub so sync can proceed (same file). Server reconciliation framing: "an elegant and flexible technique pioneered by the video game industry." ([mutators](https://zero.rocicorp.dev/docs/mutators), [sync](https://zero.rocicorp.dev/docs/sync))

**Backend coupling.** Postgres-only upstream, 15+, `wal_level=logical` required. "In the future we will support other types of upstream besides PG." ([zero-cache config](https://zero.rocicorp.dev/docs/zero-cache-config), [connecting-to-postgres](https://zero.rocicorp.dev/docs/connecting-to-postgres))

## 3. The Axes Our Spec Lives On

### 3.1 Delta / field granularity

Wire row patches are `put` (whole row), `update { id, merge, constrain }` (changed **columns** merged), `del`, `clear` (`packages/zero-protocol/src/row-patch.ts`). So granularity is column-level at best, and **a JSON column is one opaque value** — any edit inside it reships the whole column. There are no sub-column paths anywhere in the protocol.

ZQL cannot project columns at all:

> "There is no way to select a subset of columns; ZQL queries always return the entire row, if permissions allow it... This is a design tradeoff that allows Zero to better reuse the row locally for future queries. This also makes it easier to share types between different parts of the code." ([zql](https://zero.rocicorp.dev/docs/zql))

Deep/nested data status, verbatim:

- "Views are not synced." ([postgres-support](https://zero.rocicorp.dev/docs/postgres-support))
- "**No ZQL operators for arrays yet**: Zero will sync arrays to the client, but there is no support for filtering or joining on array elements yet in ZQL." (same)
- JSON filters: roadmap-"soon", not committed ([status](https://zero.rocicorp.dev/docs/status))

**Their answer for our scenario's aggregate (~150-200KB doc, ~60 top-level keys, arrays-of-id-bearing-subdocs as the dominant motif) is: normalize.** Each keyed array becomes a table with foreign keys, reassembled per-read with `related()` (many-to-many traversal capped at two chained levels — [schema docs](https://zero.rocicorp.dev/docs/schema), bug 3454). This is precisely the "relational turn" scenario.md's Aggregate-Document Principle names: the engine reassembles pre-scattered aggregates at sync speed (IVM) rather than keeping the aggregate whole. The alternative — the aggregate as one `json()` column — gets whole-blob wire granularity and whole-blob LWW, which under 10-100 co-editors is the silent-clobber hard fail (scenario.md, Concurrency Model / Failure Taxonomy). Zero has no middle path; our id-addressed array paths and deep-path projections are the middle path, and nothing in their docs argues it can't work — they simply never priced sub-row granularity.

Immutability doctrine resonates with our `safety: 'reference'`: "Data returned from ZQL should be considered immutable... If you modify a value returned from ZQL, you will modify it everywhere it is used." ([zql](https://zero.rocicorp.dev/docs/zql)) Same constraint, theirs by convention + `readonly` types, ours by dev-mode freeze + writes-through-operations (plan.md Decision 2).

### 3.2 Subscription topology + dedup

Queries dedup client-side by (name, args) hash — structurally identical to our channel address `name + '?' + JCS(args)` (ws-protocol §1). Server-side, **"Zero does not sync duplicate rows": the client receives the union of all active queries' results** ([queries, Consistency](https://zero.rocicorp.dev/docs/queries)) — but the union is computed *server-side* in the per-client CVR (client view record, stored in Postgres), where ours is computed *client-side* in the contribution/projection ledger (plan.md, Field Projections: "Server per-client state remains the subscription list, nothing else"). Their CVR is real per-client server state with a real operational tail: "GC inactive CVRs" (0.23 fix), and 1.6 fixed "Returning to an app after stale-tab GC or CVR purge caused a full page reload."

Query lifecycle: active → deactivated (unmount/cleanup/run-completion) → **cached, still syncing, for `ttl`** → evicted. Defaults: `5m` for ordinary queries, `none` for `preload()`; max `10m`; "The TTL clock only ticks while Zero is running." Rationale, verbatim:

> "Zero queries are not free. Just as in any database, queries consume resources on both the client and server... we do not actually *want* to keep queries active unless there is a good chance they will be needed again soon." ([queries, Query Caching](https://zero.rocicorp.dev/docs/queries))

This is our `linger` grace (ws-protocol §2, default 0) generalized into the primary resource-governance mechanism — they need it everywhere because every query is a server registration; we need it only where re-subscribe is expensive (recompute channels).

The cost of query-driven partial sync they document and we avoid by construction: **local results may not be a prefix of server results**, so screens shuffle when the server responds, and the prescribed mitigation is manual — "you should preload the first `n` results for that query shape with no filters, in each sort you intend to use." A real consistency model is future work: "In the future, we will be implementing a consistency model that fixes these issues automatically." ([queries, Consistency](https://zero.rocicorp.dev/docs/queries)) Our pool reads are complete over channel-scoped replicas or flagged by the v1-required coverage checker (plan.md, Client Store; priors audit #1).

### 3.3 Fan-out economics + backpressure

The unit of server compute is the **client group** (≈ browser profile), not the query: "each client group has its own pipelines; CPU and memory per group limits how many can be 'fast' at once. Since Node is single-threaded, one client group can technically starve other groups. This is handled with time slicing... `ZERO_YIELD_THRESHOLD_MS`." ([self-host, Performance](https://zero.rocicorp.dev/docs/self-host)) 1.6's "~5% CPU reduction... by reusing stringified payloads across subscribers" confirms fan-out was per-subscriber serialization until last week. Contrast: our channel instance is shared per (name, args) — "500 subscribers to `project(42)` cost one selector match per write and one delta fanned 500 ways" (plan.md, Channels), with one-serialization-shared bytes mandated by ws-protocol §1.

Backpressure and overload valves:

- Replication-manager backpressure "to protect against Postgres moving faster than we can push to clients" (added [0.18](https://zero.rocicorp.dev/docs/release-notes/0.18)).
- **Circuit breaker**: "if advancement looks like it'll take longer than rehydrating, zero-cache intentionally aborts and resets pipelines (which trades 'slow incremental' for 'rehydrate')." ([self-host, Performance](https://zero.rocicorp.dev/docs/self-host)) — philosophically identical to our reset-as-universal-pressure-valve (ws-protocol §4), with a cost-comparison trigger we don't have.
- Warm-state stickiness: "View syncers are designed to be disposable, but since they keep hydrated query pipelines in memory, it's important to try to keep clients connected to the same instance... you may need to enable sticky sessions." (same) Ours holds the opposite invariant — "no session to resume, only positions to continue from... any node answers any reconnect" (plan.md, Connection protocol) — which we get by holding no per-client warm state server-side.

### 3.4 Offline posture + outbox/rebase

**The sharpest philosophical collision with our spec.** Zero rejects writes while disconnected. The state table: reads work in `connecting`/`connected`/`disconnected`/`error`/`needs-auth`; writes only in `connecting` ("queued and... sent when the connection succeeds", default window 1 minute via `disconnectTimeoutMs`, "intended to paper over short connectivity glitches, such as server restarts, walking into an elevator") and `connected`. ([connection](https://zero.rocicorp.dev/docs/connection))

Their UX recommendation, verbatim — the line that collides with our implicit-save contract:

> "While Zero is in the `disconnected`, `error`, or `needs-auth` states, you should prevent the user from inputting data to your application to avoid data loss... The easiest way to implement this is with a modal overlay that covers the entire screen and tells the user to reconnect."

The full argument ([connection, Why Zero Doesn't Support Offline Writes](https://zero.rocicorp.dev/docs/connection#why-zero-doesnt-support-offline-writes)), verbatim, for the adversarial review:

> "Supporting offline writes in collaborative applications is inherently difficult, and no sync engine or CRDT algorithm can automatically solve it for you. Despite what their marketing says 😉.
>
> Imagine two users are editing an article about cats. One goes offline and does a bunch of work on the article, while the other decides that the article should actually be about dogs and rewrites it. When the offline user reconnects, there is no way that any software algorithm can automatically resolve their conflict. One or the other of them is going to be upset.
>
> This is a trivial data model with a single field, and is already unsolvable. Real-world applications are much worse:
>
> - Foreign keys and other constraints can pass while offline, but break when the user reconnects.
> - Custom business logic and authorization rules can pass while offline, but break when the user reconnects.
> - The application's schema can change while offline, and the user's data may not be processable by the new schema.
>
> Just take your own schema and ask yourself what should really happen if one user takes their device offline for a week and makes arbitrarily complex changes while other users are working online.
>
> It is of course *possible* to create applications that support offline writes well (Git exists!). But it requires significant tradeoffs. For example, you could:
>
> - Disallow destructive operations (i.e., users can create tasks while offline, but cannot edit or delete them).
> - Support custom UX to allow users to fork and merge conflicts when they occur.
> - Restrict offline writes to a single device.
> - Accept potential user data loss.
>
> While we recognize that offline writes would be useful, the reality is that for most of the apps we want to support, the user is online the vast majority of the time and the cost to support offline is extremely high. There is simply more value in making the online experience great first, and that's where we're focused right now.
>
> We would like to revisit this in the future, but it's not a priority right now."

Two readings matter:

1. **The argument is against *offline-first for shared data*, and our spec already concedes that ground.** Scenario.md's out-of-scope table names "shared data edited offline by multiple parties for days — unsolvable-conflict territory" in nearly their words. Plan.md Decision 10: "Offline-tolerant, not offline-first... No long-offline merge promises for shared data." Their week-offline hypothetical is outside our realistic envelope (scenario.md, Failure Model: blips, outages of minutes, dev restarts, same-day sleep/wake).
2. **Their tradeoffs list licenses our design rather than refuting it.** "Support custom UX to allow users to fork and merge conflicts when they occur" is one of their named viable paths — they declined to build that UX; our parking-first conflict surface, dead-letter retention, and field-routed confirm *is* that UX, shipped as framework machinery (plan.md, Replay conflict handling). The cat/dog rewrite is exactly what parking converts into a decision instead of a silent loss. Where their list bites hardest is the under-weighted case in our spec: **business-rule and permission rejections on aged replay** (their bullet two) — our dead-letter handles thrown rejections, but the parked-entry taxonomy is conflict-evidence-centric; rejection-on-replay deserves equal billing.

**The lineage reversal, source-verified** — this is paid-for-in-production evidence, because the same team built the predecessor: Replicache's docs promise "A tab can go offline and continue to operate for hours to days, then sync up smoothly when it reconnects" ([replicache offline](https://doc.replicache.dev/concepts/offline)), and Replicache shipped cross-client mutation recovery. Zero **disables it**: `enableMutationRecovery: false` and `enableClientGroupForking: false` hardcoded in the Zero constructor (`packages/zero-client/src/client/zero.ts:635`). They owned a working offline-tolerant outbox and turned it off. The why is the doc above plus Replicache's own caveat: "the potential for serious conflicts grows the longer users are disconnected... [convergence] won't always produce a resolution users would be happy with." Note the asymmetry against our design: Replicache-era recovery replayed *blind* (no conflict evidence, no parking, no decision surface), so their experience of it going wrong is experience of exactly the mechanism our parking threshold exists to interrupt. Their data point argues *for* the parking gate, not against the outbox.

Tracked future: [bugs.rocicorp.dev/p/zero/issue/246605](https://bugs.rocicorp.dev/p/zero/issue/246605) ("revisit this in the future").

### 3.5 Boot + reconnect choreography

Cold boot: zero-cache initial-syncs the SQLite replica from Postgres (minutes; deployment docs recommend 10-minute orchestrator grace periods — a *server* boot cost class we don't have). Client cold boot: connect → `initConnection { desiredQueriesPatch }` → server hydrates queries against the replica → pokes stream rows → `gotQueriesPatch` marks queries complete. Warm boot: render from IDB immediately, then diff desired queries. Gigabugs claim: "loading from cold start in < 2s" over 1GB+ backend data — the partial-sync payoff. ([samples](https://zero.rocicorp.dev/docs/samples), `connect.ts`, `poke.ts`)

Reconnect: cookie-based per-client-group resume (baseCookie→cookie pokes); mutation acks via `lastMutationIDChanges` in poke parts (the watermark our `welcome.lastCallID` mirrors — ws-protocol §5 cites Replicache lastMutationID directly). Schema mismatch → disconnect + `onUpdateNeeded`, default `location.reload()` — same shape as our welcome-caps reload affordance (scenario.md, Migration Window). Version skew policy is explicit: "Servers are compatible with any client of same major version, and with clients one major version back." ([self-host, Rolling Updates](https://zero.rocicorp.dev/docs/self-host))

Connection state machine: `connecting → connected → disconnected/error/needs-auth/closed`, with `reason` carried on states, Sentry-forwarding documented, `hiddenTabDisconnectDelay` (5 min) parking hidden tabs, and HTTP-error classes routed to distinct states (network errors → retry loop every 5s in `disconnected`; endpoint HTTP errors → `error`, no auto-retry, manual `connect()`; 401/403 → `needs-auth`, token refresh in place without losing state). ([connection](https://zero.rocicorp.dev/docs/connection)) Our §3 machine is close kin (blip/outage tiers, backoff), but our `failed` is terminal-until-intervention where their `error` is any endpoint HTTP failure — they pay an extra state because mutate/query endpoints are user-operated HTTP services that fail independently of the socket.

### 3.6 Schema + validation

The Zero schema is a TS artifact serving "typesafety for ZQL" and "first-class relationships" — usually **generated from the backend schema** (drizzle-zero, prisma-zero), optionally handwritten. Column vocabulary: `boolean/number/string/json<T>/enumeration<T>`, `.optional()`, `.from()` name mapping, compound PKs. ([schema](https://zero.rocicorp.dev/docs/schema)) The schema is descriptive, not authoritative: Postgres owns the shape, Zero mirrors it. Consequences they document:

- **Column defaults are unusable from the client**: "An `insert()` mutation requires all columns to be specified, except when columns are nullable... there is no way for PG to apply the default. This is a known issue." ([postgres-support](https://zero.rocicorp.dev/docs/postgres-support))
- Unsupported column types are **silently dropped from sync** ("the synced data will be missing that column and you will get a warning when zero-cache starts up") with trigger-based JSON mirroring as the documented workaround.
- Migrations are raw-SQL expand/contract discipline with deploy-order rules ("Expand: DB → API → Client. Contract: Client → API → DB"; "Incorrect deployment order will cause downtime") and a 40-line plpgsql trigger recipe for a column rename. Backfill: "The new column is not exposed to the client until all data has been backfilled." ([schema, Schema Changes](https://zero.rocicorp.dev/docs/schema))

Mutator args validation: any Standard Schema validator (Zod in examples), required because "in the server case, the parameters come from the client and are untrusted" ([queries](https://zero.rocicorp.dev/docs/queries)) — convergent with our args-schema-as-wire-contract (plan.md, Write Path) and direct confirmation of priors-audit #3 (Standard Schema is the interop layer).

There is no doc-validation tier: nothing like our collection schema as "the complete write surface" with undeclared-path filtering, computed fields, `private` floor, or `options` membership (plan.md, Schemas). Constraint enforcement is Postgres's job plus whatever the mutator body checks.

### 3.7 Permissions

Current model: **code gates at named entry points, period.** "Zero does not have (or need) a first-class permission system like RLS. Instead, you implement permissions by authenticating the user in your queries and mutators endpoints" — server-controlled `ctx` (session-derived), read permissions as filters added by the server query implementation ("Deny by Returning No Rows" — return `or()` empty, never throw), write permissions as plain code in server mutators ("Because mutators are just normal TypeScript functions that run server-side, there is no need for a special permissions system"). ([auth, Permission Patterns](https://zero.rocicorp.dev/docs/auth), [mutators](https://zero.rocicorp.dev/docs/mutators))

This is their second permissions system. The first — declarative ZQL rules compiled at build time, deployed to zero-cache — is deprecated with unusual candor: "The compilation process is very simple-minded (read: dumb)... rule functions are not actually invoked at runtime... you can't really use most features of JS in these rules... This is really confusing and we're working on a better solution." ([deprecated/rls-permissions](https://zero.rocicorp.dev/docs/deprecated/rls-permissions)) The replacement (synced queries + custom mutators, 0.18→0.23) moved authorization onto the application server. This is the field convergence our Security Posture section already banks on ("you authorize operations, not edits — the Zero/Convex conclusion", plan.md), now with the reversal documented from the primary source.

Gap relative to our spec: **no field-level permission floor.** ZQL returns whole rows; "column permissions" is a 2026 roadmap item; until then column restriction = Postgres publications, which are global (per-database, not per-role). Our role-tiered `fields` projections + schema `private: true` (fail-closed, never crosses the wire) have no current Zero equivalent. Scenario.md's role-tiered projection variants (2-3 per record) would be modeled in Zero as... nothing today; you'd split tables.

### 3.8 Presence / ephemeral tier

**Absent.** Zero `grep -ci presence llms-full.txt` → 0. Everything is Postgres rows through logical replication; there is no conflated, connection-scoped, non-durable tier. Rocicorp's presence-native product (Reflect, "Ready Player Two" — game-style state sync, 2023) was retired June 2024 ([rocicorp blog](https://rocicorp.dev/blog/retiring-reflect)); its ideas did not surface in Zero through 1.6. Cursor-chat at 20Hz through Zero would be: a Postgres write per frame, WAL traffic, replica writes, IVM advancement, CVR updates — the durable pipeline mispricing our Ephemeral Collections section names, with no escape hatch. Our `ephemeral: true` flag (plan.md) addresses a tier this architecture cannot express without a second system.

### 3.9 Pagination / windowing

Keyset-only, same conclusion our plan reached: `start(row)` (exclusive by default) + `limit()`; no offset pagination exists in ZQL. ([zql, Paging](https://zero.rocicorp.dev/docs/zql)) Aggregates (`count/min/max/group-by`) don't exist yet (roadmap-soon) — so dashboard `total`/`pages` (our searchIndex handle's window face) has no Zero equivalent; apps maintain counter rows by hand (zbugs does short numeric IDs via a counter-row video walkthrough). Windowed dashboards in Zero are live IVM queries by construction — there is no `live: false` snapshot tier; the cost knob is the TTL, not liveness. Our recompute channels with `live: false` default + `refresh` tiers (plan.md Decision 6, searchIndex factory) have no analogue; theirs is "everything is live, govern it with TTL + eviction + circuit breaker."

### 3.10 Client bundle size + boot cost

Measured today (2026-06-12, `@rocicorp/zero@1.6.2`, esbuild `--bundle --minify --format=esm`, importing `Zero` + schema builders + query/mutator definers): **299.3KB minified, 96KB gzip** (94.7% of it `@rocicorp` code, plus a Standard Schema helper dep). The widely-quoted figure from InfoQ — "718 KB uncompressed (232 KB gzipped)" ([InfoQ](https://www.infoq.com/news/2026/06/zero-version-1/)) — evidently measures the unminified dist; the honest floor is ~96KB gzip. The brief's "232KB gzip" should not be cited as their current minified cost.

What those bytes buy (from the monorepo packages the client bundles): the Replicache B-tree/DAG store with IDB persistence and rebase, the full client-side IVM engine (`zql/ivm`: memory sources, pipeline operators, views, query planning), the ZQL builder + AST, zero-protocol codecs, connection management, mutation tracking, inspector hooks. The structural reason their client is big is that **it ships a database**: a query engine that plans, executes, and incrementally maintains relational queries with joins client-side. Our client deliberately ships none of that — pool `Map`s, mongo-subset selector matching, re-run + reconcile (plan.md Decisions 2/5; IVM explicitly "Not in v1"). Even at their honest 96KB gzip, that is not an available budget at our CDN rung (scenario-hobbyist.md: bundle "small enough to not embarrass the CDN rung"); it would dwarf the framework itself.

Boot cost beyond bytes: native-dependency surface on the server (`@rocicorp/zero-sqlite3` postinstall builds, documented friction across pnpm/bun/yarn — [install](https://zero.rocicorp.dev/docs/install)), and replica initial-sync time on the zero-cache side.

### 3.11 Operational ceilings, incidents, redesigns

- **Dataset ceiling**: recommended < 100GB ("most of our customers today use Zero with smaller datasets"); architectural ceiling = SQLite replica on NVMe. Terabugs (TB-scale) is the 2026 stretch goal. ([when-to-use](https://zero.rocicorp.dev/docs/when-to-use))
- **Per-client-group CPU/memory** is the scaling unit; single-node Node time-slicing with yield tuning; sticky sessions required at scale to preserve warm pipelines; "Rehome errors" when two instances fight over a client group. ([self-host](https://zero.rocicorp.dev/docs/self-host))
- **Three Postgres databases + a SQLite file + litestream backups** is the minimum production state surface; replication slots are a named fragility (1.6 exists because "Previous Zero versions lost replication slots after a PlanetScale Postgres failover, forcing resync").
- **Redesigns shipped**: CRUD mutators (auto-generated per-table insert/update/delete on the wire) → deprecated, replaced by custom mutators (0.18), now behind `ZERO_ENABLE_CRUD_MUTATIONS: 'false'` in every deployment recipe ([deprecated/crud-mutators](https://zero.rocicorp.dev/docs/deprecated/crud-mutators)). Declarative RLS permission rules → deprecated, replaced by synced queries (0.23). Both walk-backs converge on **named operations + server code gates** — the architecture our plan starts from (no raw CRUD on the wire by construction, ws-protocol §2 `call`).
- **Incident-shaped fixes in the release log**: corrupted litestream restores, CDC-unhealthy error handling, orphaned subscribers, CVR ownership takeover races, zombie ViewSyncers inflating metrics, "Row already exists" poke assertions. ([1.0](https://zero.rocicorp.dev/docs/release-notes/1.0), [1.6](https://zero.rocicorp.dev/docs/release-notes/1.6), [0.18](https://zero.rocicorp.dev/docs/release-notes/0.18))

## 4. Rationale Archaeology

**The through-line: Zero is Replicache rebuilt with the lessons priced in, and the lessons run toward server authority and away from generality-of-state.** Their own history-of-sync framing names the four failure modes of prior general-purpose engines: "No support for fine-grained authorization; Limited support for partial sync; Required adoption of non-standard backend databases or data models; Limited ability to put custom business logic on read or write paths." ([sync](https://zero.rocicorp.dev/docs/sync)) Every Zero pillar answers one: synced queries (partial sync + authz), custom mutators (business logic on the write path), Postgres upstream (no new database), code-gate permissions (fine-grained authz).

Documented reversals, oldest first:

1. **Replicache offline-tolerance → Zero online-posture.** Predecessor promised "hours to days" offline; successor hardcodes `enableMutationRecovery: false` and tells you to overlay a modal. The stated economics: "the user is online the vast majority of the time and the cost to support offline is extremely high." (§3.4 above, verbatim block)
2. **CRUD mutators → custom mutators** (0.18): generic document edits on the wire lost to named operations. No rationale paragraph survives in the deprecation page, but the replacement docs carry it implicitly — permissions and business logic need a named server entry point.
3. **Declarative ZQL permission rules → server code gates** (0.23): "really confusing", build-time-compiled rules too restrictive. Replaced by "your server can use any auth system you want – Zero does not need to know or understand it."
4. **"Custom queries" → "synced queries" rename** (0.23→0.25 era): "they're planned to become Zero's main read API, not really 'custom'" — the queries-endpoint pattern graduated from escape hatch to the architecture.

Other stated positions worth holding onto:

- **"Just a fancy cache"**: the client can be dropped or bypassed because Postgres stays authoritative — their migration-risk story and the deep reason for Postgres-only coupling. (InfoQ)
- **`async` mutators defended as honest coloring**: "Mutators almost always complete in the same frame on the client... The reason they are marked async is because on the server, reading from the tx object goes over the network to Postgres." ([mutators](https://zero.rocicorp.dev/docs/mutators)) This is the isomorphism trade our Execution Without Fibers section makes the opposite call on (sync bodies + command buffering vs their await-everywhere) — both teams saw the same fork and named it.
- **Reads in mutators are local-only on the client, full-data on the server, by design**: "waiting for server results in mutators makes no sense – it would defeat the purpose of running optimistically." Divergence between simulation and authority is accepted and corrected by rebase — identical doctrine to our "simulations read the pool, authoritative bodies read storage" (plan.md, Write Path).
- **IVM connectedness assumption, in source**: "(2) is expected to be a cheap operation as there should only ever be a few outstanding diffs to apply given Zero is meant to be run in a connected state." (`ivm-branch.ts`) The online posture is load-bearing all the way down to the rebase fork.

## 6. Open Questions Raised for Our Spec

1. **Linger defaults per channel class** — Zero's 5m TTL is their tuned answer for query-shaped subscriptions; what is ours for recompute channels vs routed channels? (Bench + Phase 0a; row 6.)
2. **Circuit-breaker trigger for recompute-diff** — adopt cost-comparison (recompute vs resnapshot) alongside the volume threshold? What's the estimator? (Row 7.)
3. **Parked-replay outcome taxonomy** — does the dead-letter surface distinguish conflict-evidence parks from business-rule rejections on replay, and does the confirm UX differ? (Row 2.)
4. **Mutator settlement accessor** — can we expose per-call server settlement without coloring mutator call sites or weakening fire-and-forget as the norm? (Row 10.)
5. **Version-skew window** — state the reference server's client-compat policy (their same-major-plus-one-back is a sane default). (Row 8.)
6. **Union-ledger failure surface** — Zero's CVR tail (GC → full page reload) is the server-side version of our client-side projection-union pruning; do we have an equivalent "ledger corrupted → reset heals" test in Phase 4? (Row 5; ours degrades to resnapshot by design, verify it.)
7. **`reason` on connection state** — minor §6 addition, fold into the protocol v2 synthesis. (Row 9.)
