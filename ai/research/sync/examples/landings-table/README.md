# Landings table — the standard trifecta

Table view + three-dots row menu → edit modal + add-new button → insert modal, page updates. The canonical operations CRUD page, steelmanned against the scenario's collection. Revised to exercise the full search-index declaration surface.

A landing is one vessel's catch coming across the dock: which boat, which port, how much, and whether it has been filed and paid. Three statuses, `draft → submitted → settled`, and a filing clock — the logbook is due within a day of landing, which is why `isFilingLate` is measured in hours.

## What it stresses

- **The search index is its own verb**: `Landings.searchIndex('table', { permission, filter, search, fields, where, sort, pageSize, engine })` plus the liveness knobs (`live`, `refresh`) declares the whole surface — auth token, baseline selector, searchable fields, returned projection, client-drivable filter/sort whitelists, built-in pagination (`landings.total`, `landings.pages` ride the handle). `query: ''` is the default window: the primitive is the indexed table view, text search is one parameter. Underneath it compiles to a plain channel — same sharing, cursors, recompute-diff, projection ledger. The formalization gradient, server-side: ad-hoc channel : searchIndex :: component : primitive.
- **Window liveness via shared recompute-diff**: write-time field-intersection triggers a debounced re-run + id-diff per channel instance — shared across all subscribers of the same search, never per-client, never on a timer. Resolves the deferred windowed-channels question with a mechanism instead of a cut.
- **Two read surfaces, one collection**: the table subscribes the search index (`landings.table` — window args: query/where/sort/page), the edit modal subscribes the `detail` publication (`landings.detail` — its own args: `{ id }`). The derived addresses tell the subscriber which arg contract they're in. The client pool unions projections per doc — the contribution ledger earning its keep on a real page.
- **Channel config, all of it declared**: `permission` tokens (auditable, resolved by the app's `can()`), `filter` baseline selector (soft-delete/tenant scoping declared once), `fields` inclusion list, `private: true` computed search blob (a search-denormalization field as two schema keys — computed fields are stored by definition).
- **One modal, two modes**: `landing-id` present forks the doc, absent forks schema defaults. Edit commit goes touched-paths through `Landings.save`, insert binds explicitly to `Landings.create`.

**Security note that declaration buys:** matching against an unprojected field leaks its contents through result membership (search-as-oracle). Declared `search:` fields make searchable-but-never-sent (`searchText`, `private: true`) an explicit choice instead of a lazy `ILIKE` accident.

**The folder convention, demonstrated:** `collections/landings/landings.js` (schema + helpers), one file per mutator under `mutators/`, one per publication under `publications/`, the search index under `search/` — late attachment via `Landings.mutator/publish/searchIndex(name, ...)`, loaded by the glob line in `client.js` (operations only) and `loadCollections()` in `server.js`, sealed at listen. Adding an operation or a publication never touches a shared file, and `server.js` holds no domain content — it reads the same as `client.js`, infrastructure only. Schema types are constructors (`String`, `Date`, `Number`) — the authoring idiom everywhere, serialized to string names only on the wire. Note the rename forced by the reserved-name rule: the public mutator is `save`, never `update` (raw `Landings.update` is the privileged CRUD inside bodies — the rule caught a collision in this example's earlier draft).

**Deliberate absences (meaningful, not missing):** no `queries` section — the search channel queries server-side, so the trinity's queries slot is empty here, which is itself the lesson (not every component shapes pool data). No ephemeral/presence tier, no id-addressed array editing — those belong to the trip-editor scenario (detail page, the haul and catch grids).

## Sore points to feel (the 0a review list)

1. **Insert into a searched window is genuinely ambiguous.** The client cannot evaluate search membership locally (relevance lives server-side), so the optimistic row cannot appear in-place. Options: appear-on-confirm (sub-second via the live channel) or optimistic-pin at top with a pending affordance outside the search ordering. Pick by feel.
2. **The edit modal loads.** Detail fields aren't local until `landings.detail` snapshots — the modal shows a spinner for one round trip. Is that acceptable, or should the form render the table-known fields immediately and hydrate the rest?
3. **Insert-form → mutator binding.** Edit mode has a natural commit target (touched paths → `save`). Insert mode binds explicitly (`Landings.create(draft.values())`). Is explicit right, or does `{#form collection=... via='create'}` earn its sugar?
4. **Regime agnosticism — resolved by the `engine` knob, verify the feel.** `engine: local()` would run the same declaration client-side against a synced working set, component code unchanged. Does the declared arg surface (query/where/sort/page) cover real tables, or does it sprout warts (multi-column sort, facet counts, OR-filters)?
5. **Count/meta surface.** `landings.total` and `landings.ready` ride the subscription handle. Right home? What else belongs there (page bounds, query time)?
6. **Sort state shape.** `{ field: dir }` object in component state, translated by the handler. Feels thin — check it survives multi-column sort.
7. **Match vocabulary sufficiency.** `exact` / `prefix` / `word` / `text` + `weight` is the whole portable contract — engines implement it (substring scan, pg tsvector/trgm, elastic native), analyzers stay in engine config, index-time analysis is a computed field (stored by definition). Does four words cover real tables?
8. **Helper reactivity granularity.** `{landing.isFilingLate}` inside the each-block — per-field deps (if `this` is the item proxy) or the coarse whole-item dep (the `{formatDoc todo}` precedent)? Both correct, one finer. Needs the trace + test before the claim.
9. **Relevance as live sort** — applies only under `live: true`. The default (`live: false`, `refresh: 'own-writes'`) sidesteps mid-view reordering entirely: the table updates on your own writes and on interaction, co-editor churn waits. Feel both modes.
10. **A time-derived flag is not reactive.** `isFilingLate` flips on a clock, not on a write, so a row already rendered will not restyle itself when the deadline passes. Live-by-default hides this in the table (any write re-renders), the nonreactive default does not. Reactive-clock or accept the staleness?
