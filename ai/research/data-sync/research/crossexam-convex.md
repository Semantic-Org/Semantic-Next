## 1. The Headline — The Isolation Hole (open question 1, candidate #1)

### What the spec actually says, and where it stops

plan.md Execution Without Fibers: writes buffer as commands, the body completes, "the framework applies the command log to storage in one async transaction — read-modify-write per update, with `fn` executing inside the transaction." plan.md Sync Loop: "Server runs authoritative impl in a transaction." Both sentences are about **one** operation. Nothing anywhere states what two concurrent authoritative operations observe of each other on the same document — what "inside the transaction" means when a second transaction is running. Convex answers serializable OCC and says anything weaker "is just too hard a programming model." We currently answer nothing. The attack is correct and the candidate stands — but "adopt the discipline, write a paragraph" undersells what must be decided. Here are the options, priced.

A structural fact that shapes all of them: the plan already quarantined every mutator storage read into update callbacks executing at apply time (bodies may not read storage outside an update callback — Execution Without Fibers). There is no read-before-apply to invalidate. The entire isolation question collapses to one point: **what state does an update callback see, and what may interleave between its read and its commit.**

### Option A — serial-per-doc apply (recommended)

Update callbacks on a document execute serially against its latest committed state. Reference server (single-threaded Node, memory adapter): an in-process apply queue per doc — nearly free. Postgres adapter: `SELECT ... FOR UPDATE` row lock inside the transaction — the lock is the queue, and it stays correct under multi-node (any node can apply, the storage row lock serializes them, no doc-affinity routing needed). The contract: *an update callback observes the latest committed state of its document, and its writes commit before any other callback on that document runs.* Single-doc operations are fully serializable, with zero retries, by construction.

Priced against the scenario:

- 10 typers × 1 commit/300ms = 33 ops/sec on the hot doc (scenario.md Canonical Load Figures) — trivial for a serial queue.
- 100-co-editor ceiling = 330 ops/sec serial. A single RMW storage round trip at 1-3ms saturates near the ceiling, but serial in-process callbacks group-commit naturally: run N queued callbacks back-to-back against the evolving in-memory doc, write the final doc + N delta records in one storage transaction. Serial order = queue order, serializability preserved, N round trips collapse to one. Latency stays far inside the sub-second detail staleness bound.
- No retry storms, no starvation, FIFO fairness — the exact failure Convex documents for OCC under sustained contention ("...and on every subsequent retry", error docs) cannot occur.
- The 300ms client debounce means arrivals are smooth, not bursty — the friendliest possible arrival process for a queue.
- Migration window: `update(selector, fn)` over ~500 docs per transaction holds ~500 row locks for the transaction's duration (tens of ms) — bounded, off-peak, and the scenario's "small transactions, paced" rule gains a second justification (lock hold time), it doesn't fight this.

Priced against the write pipeline: nearly free, because the pipeline already has the right shape. Command buffering means the apply point is the only place storage state is observed. Serializing applies per doc is arguably just the precise meaning of the words "read-modify-write per update ... inside the transaction" that the plan already wrote. Cost named honestly: a slow update callback head-of-line blocks that document's queue — every co-editor's write latency on the hot doc. This wants a stated callback execution budget and a dev-mode slow-callback warning (see finding N4, the limits table).

Edges stated, not hidden: `mutate(doc, args)` bodies are statically single-doc (plan.md Write Path exploits exactly this guarantee) — they get the full contract. `run` bodies touching multiple docs get per-doc serial callbacks + atomic commit under one txid, but **no cross-document snapshot**: callback on doc A and callback on doc B may observe states from different moments. Cross-doc invariant enforcement is explicitly out of the mutator contract — which matches the plan's existing line that needing to branch on storage state is the signal the operation wanted to be an action. Two multi-doc operations can deadlock under row locks (selector resolution at apply time prevents canonical lock ordering) — storage-level deadlock detection + single retry is the answer, rare because multi-doc hot contention is not the scenario's shape.

### Option B — per-collection serial queue

Simpler, and wrong for the scenario: all writes to `records` serialize, including different docs. Fifty operators on fifty different records would queue behind each other, and a migration batch would head-of-line block every live operator in the collection. Gratuitously discards the parallelism the document model grants. Reject.

### Option C — document-level OCC with retry

Convex's shape at doc grain without their read-set precision. At 33-330 disjoint-field writes/sec on one doc, every concurrent pair conflicts at doc-version grain — the same ~100%-false-positive math the plan already used to reject per-doc versions for replay conflict evidence applies identically to OCC validation. Under sustained contention retries either starve (their documented failure mode) or serialize anyway, paying retry overhead for what Option A gets free. OCC earns its keep when there is no cheap co-located serialization point — but the storage row lock is exactly that point, on every adapter we ship. Reject.

### Option D — path-granular LWW interleave (the do-nothing option made explicit)

Operations interleave freely, paths land last-write-wins, single-transaction atomicity only. This breaks on read-modify-write, and the spec has made every write a potential RMW: computed fields run at write time reading the doc (plan.md Schemas). Two interleaved operations produce write skew on derived fields — A recomputes `total` from a pre-B `items`, B's insert lands, A commits the stale total. Silently wrong derived data on the everyday disjoint-row shape is a hard fail (scenario.md Failure Taxonomy: destruction of information, zero silent budget). It also leaves `mutate(doc)`'s resolved doc snapshot undefined. Reject — while noting Option A does not change Decision 1: path-granular LWW remains the **cross-operation** conflict semantic (what happens when two committed writes touched the same path). The isolation contract pins what a single authoritative body may rely on *while running*. Different layers, both now stated.

### Recommendation and the argument that dissolves their quote

Adopt **Option A**, as a spec amendment to plan.md (Execution Without Fibers or Sync Loop, server side) plus a conformance MUST in the protocol-v2 synthesis:

> **Authoritative isolation contract.** Update callbacks on a document execute serially against its latest committed state (apply queue or storage row lock per adapter). A single operation's writes commit atomically under one txid. Single-document invariants enforced in an update callback hold under any concurrency. Cross-document invariants are not protected by mutators — an operation that needs them is an action by definition, and v1 actions get the same per-doc contract, not cross-doc snapshots.

Then the part that belongs in the decision record's "why": **the Aggregate-Document Principle makes per-doc serializability sufficient by construction.** The scenario chose one document as "the consistency boundary made physical" (scenario.md). Convex needs cross-table serializable transactions because the relational turn scatters an aggregate's invariants across rows — their isolation scope must reassemble what their data model dispersed. Ours concentrates the aggregate's invariants inside one serialization domain. We can agree with their architect completely — less than serializable *is* too hard a programming model — and deliver serializability at exactly the boundary the domain declared, with a FIFO queue instead of a retry loop. Their strongest quote, absorbed rather than rebutted.

## 2. The Durability Sibling — storage-commit ↔ channel-log-emit (new finding N1)

The spec's second silence, and the dossier missed it because Convex structurally cannot have the problem: their append-only transaction log **is** both the durability record and the subscription feed — commit and publish are one write by a single-writer committer. Our design has two durable systems: storage, and the channel log (Redis stream under multi-node). plan.md Sync Loop: "Server runs authoritative impl in a transaction, routes deltas to channels" — two steps. A crash between them yields a committed write that never enters any channel log. Subscribed clients hold valid cursors and never receive it: silent, unbounded staleness on a live channel. That violates both soft-fail rules at once (unbounded, undisclosed — scenario.md Failure Taxonomy) and reproduces, inside the core, the exact "silently stale clients whose data appears on refresh — the worst failure shape" that the External Writers section condemns for direct storage writes.

Adopt the goal, not the mechanism. The goal: **a committed transaction's deltas MUST become visible in every affected channel log, or the affected channels' epochs must change** (reset → resnapshot, the existing universal healer). Three postures, priced:

- **Single-node reference server (the hobbyist rung): free by mortality.** Channel logs are in-process ring buffers — they die with the process. Restart mints a new epoch inside the opaque cursor (ws-protocol §5 already carries epoch-in-cursor for exactly the server-amnesia class) → every reconnect resnapshots. Crash consistency holds with zero machinery. The spec should say this is load-bearing, not luck.
- **Multi-node + Redis: transactional outbox.** The delta record (txid, channel addresses, changes) commits in the same storage transaction as the write. An at-least-once dispatcher publishes to the stream and advances a dispatch watermark. Duplicate emits are already safe (at-least-once + equality-checked client apply is protocol law). Cost: one extra row per transaction plus a dispatcher loop — and the same dispatcher is the substrate the scheduler bridge wants (§5 below). One mechanism, two consumers.
- **CDC-as-emit-source** (derive all emits from `watch()`, making the WAL the single source — the Electric-flavored answer): rejected as the primary path because CDC events carry no attribution or txid (plan.md External Writers states the asymmetry), which would break confirmation and rebase. Stays the backstop it already is.

Feeds protocol-v2 directly, paired with §1: the two server-side MUSTs the conformance suite checks that no wire transcript can.

## 3. Confirmed-Divergences Attacked

### #2 Queries-as-subscriptions vs channel replicas — attack fails, divergence upheld

Their architect, reviewing our spec for our scenario: *"Your bench math straw-mans us — nobody subscribes one 170KB query. Decompose the record page into narrow queries per subpage and our cache fans small results. Meanwhile your channel model forces developers to solve preloading by hand (we wrote the essay on why that's hard) and you inherit the silently-incomplete-query trap your own priors audit admits — your fix is a dev-mode linter. Coverage cannot drift in our model."*

The decomposition dodge fails on their own documented mechanism. Read sets are doc/index-range granular, not field granular — the committer checks whether a log write "would have changed the result of either our `get(...)` or `query(...)` reads" (How Convex Works), and any field write to the doc is a new version that changes a `get`. So N narrow queries against the hot doc **all** re-run on every one of the 33-330 writes/sec, each re-execution metered, each pushing its full (smaller) result. The byte mass concentrates in the 3-4 heavy subtrees that are the page content (scenario.md Parameters), so per-subscriber wire cost stays in MB/s territory against our 5-10KB/s field deltas, and the server-side bill multiplies by the decomposition factor. Their own roadmap concedes the endpoint: "pushing smaller deltas to the client" — which requires exactly the write-time path granularity our wire starts from. At our substrate the deltas land as top-level field reference swaps on per-field deps (apply discipline, ws-protocol §2), waking only the ~10 bindings a page reads out of ~100 fields — the lens rule satisfied natively, no re-derivation needed.

What survives the attack and should be acted on: the coverage trap is structurally impossible in their model and only checked in ours. The checker is already v1-required (plan.md Client Store), but its *production* posture is unstated — "dev-mode warning" is the only named form. Finding N6: the spec should state what production builds do (nothing, cheap sampled warn, or telemetry), so the trap's residual risk is a decision rather than a default.

### #3 OCC serializable vs path-granular LWW — attack softens one claim, divergence upheld (open question 4)

The honest attack, with this pass's verification behind it: conflict validation is **read-set only** — "the writes all commit if every version in the read set is still the latest version" (OCC docs), and the committer description in How Convex Works confirms write sets are log payload, not conflict input (the error message's "read from or written to" phrasing is looser than the documented mechanism). `db.patch` is a shallow top-level merge (writing-data docs). So their architect says: *"Write blind patches. Disjoint top-level fields don't conflict — your retry-storm figure assumes naive read-modify-write nobody would ship."*

Concede the narrow point: granting that `patch` doesn't internally enroll the doc in the read set (undocumented — schema validation of the merged result suggests an internal read, but charity demands the assumption), blind patches to disjoint **top-level scalar** fields are conflict-free under their OCC. The scenario has ~100 top-level keys, majority scalar — a real slice of everyday co-editing could be written conflict-free in Convex. The dossier's "would conflict pairwise" needs this refinement.

Then the counter, on the surface where the scenario actually concentrates concurrency: **the arrays.** "Two people in different line-item rows simultaneously is constant" (scenario.md Concurrency Model). `patch` has no row vocabulary — `items[id=r7].amount` does not exist in their wire. An idiomatic Convex mutator on a keyed array either (a) reads the doc, modifies the array, patches it back — the read enrolls the doc, pairwise conflicts return, retry storm at 33/sec on the hot doc, or (b) blind-patches the whole array — and two concurrent disjoint-row edits clobber, the exact whole-array hard fail the taxonomy gives zero silent budget. Their model forces a choice between the retry storm and the silent clobber precisely where our id-addressed paths dissolve both. Second counter: blind-patch-only mutators are write-only — no `check`, no computed-field derivation, no cross-field validation. Our four-phase pipeline reads by design, and so does any real back-office invariant. The discipline that makes their hot doc survivable is the discipline of having no validation.

Disposition: confirmed-divergence upheld, with the dossier's claim sharpened — retry-storm applies to any mutator that reads the hot doc, blind-patch escape exists for top-level scalars only, and the array surfaces convert the escape into a hard fail. Plus §1 closes the hole their quote legitimately exposed on our side.

### #6 Durable outbox — attack fails, divergence upheld, and the cousin is converging on us (open question 5)

Their architect: *"The reload-loss window is one RTT in practice — mutations settle in ~100ms. Your IDB outbox buys that window with a durable write per commit, leader-tab choreography, eviction tombstones. A beforeunload prompt covers it."* The attack fails on the scenario's failure envelope: the queue is largest exactly when durability matters — during the minutes-long outage, the dev-server restart, sleep/wake (scenario.md Failure Model). A reload mid-outage with an in-memory queue loses *all* queued work, and implicit-save means the user was never holding unsaved state knowingly. "A minutes-long outage costs one badge and zero work" is the bar, and their posture fails it by construction.

And the cousin's own trajectory now testifies: **curvilinear persists state in IndexedDB and replays in-progress mutations on restart** — mutations are centrally defined "since the sync engine needs to know how to replay in-progress mutations on restart" (README, verified this pass). IDB persistence means reload survival, not just process restart (the README doesn't distinguish, the storage choice does). Their local-first alpha independently arrived at Decision 3's durable outbox, replay-by-named-mutation and all — alpha-grade ("haven't wrung out all the bugs yet"), but directionally a concession. Divergence upheld, now with convergence evidence.

### #7 Single isomorphic optimistic body — attack fails, divergence upheld

Their architect: *"The dual implementation is honest separation: optimistic updates are a UI concern (patch what users see), mutations are a data concern. Your single body forces command buffering — our mutation bodies read the database freely mid-transaction, yours can't read storage at all outside callbacks. And your simulation diverges from authority anyway (your own plan says so), so you bought 'write once' and still pay divergence-correction."* Three answers. The plan already states the buffering trade openly (Execution Without Fibers, "The isomorphism trade, stated") — it is a priced cost, not a discovery. The divergence in our model is bounded and self-healing by the same rebase machinery that exists regardless (their rollback plays the identical role — "rerun if the local query results change" *is* a rebase at query grain, the dossier's catch stands). And the vendor's own essay lists implement-twice and schema divergence under hard problems, while their docs carry a state-corruption footgun ("Always create new objects") that our trackWrites envelope makes unexpressible. Decisive detail: **curvilinear still ships dual-component mutations** (server pointer + local callback) in their local-first alpha — they are carrying the tax into their next act. The single isomorphic body is the genuinely differentiated bet. Upheld.

### #8 Ephemeral tier — attack fails, divergence upheld, one honesty note

Their architect: *"You're minting a third pipeline — new frame physics, conflation semantics, connection-scoped expiry — for cursor-chasing, while we ship presence as a library on the one pipeline we have. And does your hobbyist pay bytes for it?"* The attack fails on arithmetic their own component documents: durable-pipeline presence is heartbeat mutations + transaction-log writes + scheduled-function machinery built specifically "without re-running queries every time a user sends a heartbeat" — cost-avoidance engineering for a mispriced pipeline, with single-flighting capping update rate near one-per-RTT. 20-30Hz cursors are not attemptable through it at any price. Our flag re-prices physics the durable pipeline cannot tune its way into (no log, no cursor, conflate-don't-queue), and the client surface stays identical (`{#each cursor in Cursors.find()}`, one peer's move = one field dep = one style write — the substrate absorbs 100 single-field fires/sec without blinking, plan.md Ephemeral Collections). Hobbyist cost: a flag never used is a code path tree-shaken — but that is an assertion until the bundle line-items exist (#5 below). Honesty note that survives: ws-protocol.md has **no ephemeral frame type** — plan.md says "pending an ephemeral frame type." The divergence is real but currently a promise. The protocol-v2 synthesis should treat the ephemeral frame as a named deliverable, since two confirmed-divergences (#8 here, presence economics) hang from it.

### #12 Runtime read sets vs static selectors — attack fails, divergence upheld

Their architect: *"Your static analysis is brittle — your own retraction admits $or/$in subsumption is real work, sort-field deps were unstated, and the moment a handler does anything interesting you fall back to recompute channels: re-run-on-write-flag without read sets. You rebuilt poll-and-diff and called it a tier."* The jab's answer is already in the plan: recompute runs per channel instance, write-triggered, debounced, diffed — not Meteor's per-observer-per-client timer loop — and it is **default-off** (`live: false`), so the expensive precision case is opt-in where the economics earn it (Decision 6). The 90% case in the scenario is `records.byId` — an id-equality selector, trivially matchable at write time. Their precision for arbitrary handler code is real and conceded in the dossier, and its price is the entire platform: read sets exist only because user code runs inside their instrumented runtime, the exact coupling Decision 9 refuses and the hobbyist's "zero deps beyond Node" cannot carry. At our granularity the equivalent outcome — wake exactly the bindings that read a changed field — is reached by write-time path routing into per-field deps, which their roadmap is still chasing. Upheld.

### #16 Platform coupling + adoption floor — attack fails, divergence upheld, funnel honesty added

Their architect: *"Protocol-first is unproven — DDP was a 'protocol' and no second implementation ever mattered. Conformance suites don't summon implementations. Our coupling is where serializability and read sets come from — you kept a maintenance boundary and gave up every guarantee that needs the runtime."* Two answers and a concession. Their own open-sourcing retro names lock-in fear as an adoption suppressant — the maintenance-boundary worry is real at enterprise, conceded by their reversal. And §1 just demonstrated the guarantee that matters at our consistency boundary (per-doc serializability) falls out of a row lock, not a runtime. The concession worth recording: `npx convex dev` is genuinely minutes-to-first-sync *within* npm+TypeScript land — the hobbyist bar competes against a real funnel, not a strawman. Our differentiator is the rung below their floor (script tag, no build, no account, one server file), and scenario-hobbyist.md's bars are the spec's answer. Upheld.

## 4. Adopts Attacked

### #1 Isolation statement → re-dispositioned **adopt-the-goal-not-the-mechanism**

Worked fully in §1. The goal (a stated isolation contract bodies can rely on) is adopted. The mechanism is not OCC — it is per-doc serial apply, which the aggregate-document scenario makes strictly better at the hot doc. Amendment drafted above.

### #4 Migration guardrails — upheld as adopt, mechanism re-derived

Cargo check: "schema push validates all existing documents" assumes a deploy step and a platform that owns the data. We have neither — schemas are app code, the server learns them at `listen()`. The adopt re-derives as: (a) a validation pass at `listen()` or via CLI — scan or sample existing docs against the loaded schema, warn by default, `strict` refuses to listen (hobbyist never sees it: memory adapter, no pre-existing data), (b) the dual-write migration doctrine as documentation beside the Migration Window, (c) their field-removal-blocked-while-data-exists check becomes a warning in the same scan (schema dropped a field that N docs still carry). Cheap, no protocol impact, and it is the enforcement loop that makes #17's `required: true` honest (below). Adopt.

### #10 Scheduler as the mutation→action bridge — confirmed adopt, designed in our vocabulary

The pattern in our terms: a mutator records intent and schedules the follow-up, the action does the external work. Design that survives our constraints:

- **Scheduling is an insert into a framework-owned jobs collection** — not a new API surface. `schedule(name, args, { after })` inside an operation body is sugar for an insert through the same ambient envelope, which means it buffers as a command, commits in the same transaction as the intent write, rides the operation's txid, and is deduped by the mutator's idempotency ledger on outbox replay. Durability, atomicity, and exactly-once-effect all fall out of machinery the spec already has.
- **The dispatcher is the §2 outbox dispatcher** — the same at-least-once loop that publishes delta records drains job rows. One mechanism, two consumers, and the scheduled action's own idempotency key (the operation id, already named in Execution Without Fibers) covers dispatcher retries.
- **Client simulation**: the jobs collection is server-only, so the client's optimistic insert lands nowhere visible — the simulation shows the intent write (status flips to 'sending'), never the job. A detail for the Phase 0a steelman corpus to exercise.

Checked against the bimodal-practice claim (plan.md Write Path: "Practice is bimodal, the middle rungs are rare"): the bridge does not create a middle rung. The mutator stays fully simulated (its writes), the action stays unsimulated (its effects) — the bridge is server-side plumbing between the poles, invisible to the client contract. And it fixes a hole client orchestration cannot: *call-mutator-then-await-action breaks offline* — the mutator outboxes and replays later, the action rejects fast while disconnected, and the business effect silently never happens. Mutate-then-schedule makes the follow-up ride the mutator's durability, which is the only composition that survives the failure envelope. Adopt, with the jobs-collection sketch as the reference-server minimum. Their full scheduler/crons/workpool remains platform-tier — say so, per the dossier's pricing rule.

### #13 Published operational ceilings — upheld as adopt, one entry added

Trivially cheap, already justified. Addition from §1: under serial-per-doc apply, a slow update callback is every co-editor's latency on that doc — the limits table gains a **per-callback execution budget** (Convex's 1s mutation cap and sub-100ms Zen guidance are the precedent) plus a dev-mode slow-callback warning. Finding N4.

### #15 Read-your-writes convergence note — upheld as adopt (lineage prose, zero machinery)

Three independent designs landed on settle-after-effects-visible (Replicache lastMutationID, Convex ts-gating, our txid rule). Record it in the spec's lineage notes. Nothing to attack — it costs words.

### #17 Required-by-default — resolved: keep optional-by-default, amend the guidance line (was reconsider/examine)

The seat question: does their rationale survive our check()-carries-presence-rules design, or expose a hole? **It exposes a hole, and the hole is in our prose, not our default.** plan.md Schemas: "real presence rules live in mutator `check`." But `check` is per-operation — a presence rule enforced in `todos.add`'s check is silently bypassed by any other operation that inserts or clears the field. The doc gate (collection schema) is the only surface every write passes through. So the amendment: **cross-operation presence invariants belong in the schema (`required: true`, enforced at the doc gate on insert and on writes clearing the field), op-specific presence stays in `check`.** The current line overpromises check's reach.

The default itself stands on the scenario: thousands of field definitions under jurisdictional permutation where most fields are legitimately absent on most docs (scenario.md Document Shape) — required-by-default would mint thousands of noise markers, and the hobbyist's schemaless-first gradient points the same way. Convex's inverse default works *because* push-time validation enforces it against production data — adopt that lesson through #4's validation loop, which is what makes our opt-in `required: true` a true statement rather than an aspiration. Disposition: confirmed-divergence on the default, with the guidance amendment and the #4 dependency recorded.

## 5. Reconsiders Resolved

### #5 Bundle budget framing → **adopt the framing, number needs-jack**

The dossier's point is correct and uncomfortable: Convex is the existence proof that a sync client can be 18.3KB gzip, and the CDN rung will be compared to it — Zero's 232KB is not the category floor. The architecture we chose (matcher, rebase engine, outbox, cursor machine, IDB layer client-side) is the one that grows clients, and the runtime-first thesis makes those bytes user-facing. Resolution: the plan gets a **line-item byte budget table** (matcher / rebase / outbox+IDB / cursor+resume / consumer surface / schema), each feature priced minified+brotli, with the tree-shaking law (hobbyist pays nothing for parking, projection unions, searchIndex window faces) enforced per line item rather than asserted. Two honest offsets for the comparison: our renderer integration ships with the framework regardless (the marginal sync bytes are the fair metric, where Convex's React hooks add 2.6KB to theirs), and their thin client buys no boot story (network-bound every load) where our bytes buy hydrate-from-IDB render-first. The bar number itself is a product call: needs-jack.

### #9 Cross-query consistent snapshots → **reject the mechanism, adopt the disclosure**

Their whole-query-set atomic Transition is another monolith dividend: one log, one clock, one committer. Re-deriving it across independent channel logs means cross-channel coordination at resume — a cursor vector, which ws-protocol §2 already rejected for breaking cursor opacity (the one door that keeps delivery pluggable). The full-strictness alternative (barrier the first paint until all boot channels' `live` arrive) is exactly the boot latency the hydrate-render-immediately machine exists to kill. Resolution: classify the torn-boot window as a **bounded soft fail** in the failure taxonomy — bounded by the boot window, healed at each channel's `live`, exposure structurally narrowed by the topology (one dominant channel + small reference collections, scenario.md Channel Topology). Disclose it: per-channel `ready` on handles is the affordance, and an app-space recipe (gate a composite view on the relevant handles' `ready` — a plain reactive read) covers the rare surface that genuinely cannot tolerate mixed snapshots. The spec says this explicitly instead of inheriting the tear silently. txid grouping continues to cover live-write atomicity, which is where cross-channel tearing would actually destroy meaning (a multi-collection operation half-applied).

### #11 searchIndex bounded scan → **adopt**

Limits-honesty, spec-level, near-zero cost: the searchIndex contract gains declared per-engine ceilings (max docs scanned per recompute, max terms, max filter fields — their 1024/16/16 are the precedent shape), hosted in #13's limits table, with stated degradation when a cap is hit (truncated window + a disclosed flag, never silent). Their always-reactive search rides platform read sets and stays the economic divergence — our `live: false` default is already the answer (Decision 6) and is untouched by adopting the ceilings.

### #14 Pagination journal semantics → **adopt the semantics statement, mechanism already matches**

Their QueryJournal freezes page boundaries at first execution so pages stay reactive without overlap or gaps — "Page sizes in Convex may change!" is the cleanest articulation of the reactive-pagination contract in the field. Our keyset-anchored windows reach the same behavior (anchors are data positions, live inserts inside a window enter via routing, load-more anchors at the previous window's edge — contiguity holds). Steal the contract prose for the windowed-channel docs: *window boundaries freeze at subscribe, windows grow and shrink under live writes, adjacent windows stay contiguous.* No mechanism change, three sentences of spec.

## 6. Open Questions Worked

**1. What isolation does our reference server promise when two authoritative mutator bodies interleave on the same doc?** Answered — currently none is stated, and §1 drafts the amendment: per-doc serial apply (Option A), serializable at the document boundary, group-commit for the 330/sec ceiling, cross-doc explicitly out of contract. Recommended for protocol-v2 alongside the §2 commit-visibility MUST.

**2. Does Convex's sync worker suppress byte-identical re-run results before pushing?** Answered with a named residual: not documented, and the protocol neither confirms nor denies — `Transition { startVersion, endVersion, modifications }` structurally permits advancing the clock with no modification entry for an unchanged query, but no doc or protocol comment states the sync worker does so (verified against How Convex Works, query docs, and protocol.ts this pass). The spec-relevant lesson holds either way: identical-result suppression must be pinned explicitly somewhere, and ours is, twice — recompute-diff emits nothing on a no-change re-run (plan.md Search channel mechanics) and client-side `Signal.set` deep-equal dedup absorbs duplicate applies (reactivity-review, `set-dedup` upheld). We don't inherit their ambiguity.

**3. Is the 1024-fields limit top-level or total nested?** Answered: per object level. The limits page applies its document limits "per document and to any nested `Object` unless stated otherwise" — and the coexisting 8192-array-elements limit makes the total-leaf reading impossible (an array of subdocs would trivially exceed 1024 total). Our aggregate — ~100 top-level keys, subdoc rows of modest width, depth ~10 against their 16 (scenario.md Parameters) — fits comparable engine ceilings comfortably at every level. The several-thousand-leaf-path figure is total paths, which no per-level limit touches.

**4. Can blind db.patch make disjoint-field co-editing conflict-free under their OCC?** Answered in §3 (#3): yes for disjoint top-level fields, granting the undocumented assumption that patch doesn't internally enroll the doc in its read set (read-set-only validation is confirmed, patch's internal read behavior is not documented). The retry-storm claim narrows to mutators that read the doc — which includes any validated, derived, or array-row write. On the scenario's array surfaces, blind patch converts the retry storm into a whole-array clobber hard fail. Divergence upheld, claim sharpened.

**5. Does curvilinear's mutation replay survive page reload?** Answered: yes by storage choice. State persists in IndexedDB and mutations are centrally defined so "the sync engine needs to know how to replay in-progress mutations on restart" (README). IDB survives reloads, so the replay does — the README doesn't distinguish reload from process restart, the storage does. Their local-first direction has converged on Decision 3's durable outbox shape (named-mutation replay over a persistent store), at alpha maturity, still with dual-implementation mutations. Convergence evidence for #6 and #7 both.

## 7. New Findings

**N1 — Commit-visibility crash consistency** (§2). adopt-the-goal-not-the-mechanism. Their log-unification dissolves a dual-write problem our two-system design carries silently. Amendment: the conformance MUST + single-node mortality note + multi-node transactional outbox. Anchor: scenario.md Failure Taxonomy (soft fails must be bounded and disclosed — an unemitted committed write is neither).

**N2 — Auth principal change vs surviving subscriptions.** ws-protocol §2 `auth` refresh keeps subscriptions, cursors, and in-flight calls untouched (Centrifugo lineage) — correct for token *refresh*, unsound for principal *change*: a re-auth as a different user leaves channels authorized under the old identity streaming. Convex versions identity separately from the query set so identity changes re-evaluate queries. Amendment for protocol-v2: `auth` MUST present the same principal, otherwise the server re-evaluates channel permissions (revoke via `nosub 4202`) or closes for a fresh handshake. One sentence, closes a privilege hole. Anchor: scenario.md role-tiered projections — staff vs restricted views of the same record are different principals by construction.

**N3 — In-flight action disposition on connection drop.** plan.md says actions reject fast *when called* disconnected. Silent on in-flight-at-drop. Convex cancels actions on reconnect (at-most-once, caller's problem). Our ledger already caches results for its TTL (ws-protocol §4), so the right statement is: in-flight action promises reject with a connection error code on drop, never silently retried — and the result-cache is what makes the caller's manual retry safe. One line for protocol-v2. Anchor: scenario.md Write Pattern — business actions are awaited with pending UI, an unresolved promise is a hung spinner.

**N4 — Callback execution budget.** Consequence of §1: serial-per-doc apply makes a slow update callback head-of-line latency for every co-editor on that doc. Limits table entry (per-callback budget, Convex's 1s/100ms precedent) + dev-mode slow-callback warning. Anchor: scenario.md detail staleness bound (sub-second) — one 500ms callback at 33 ops/sec is a queue, not a blip.

**N5 — Ephemeral frame is load-bearing and unwritten.** Two confirmed-divergences (#8, presence economics) rest on a frame type ws-protocol.md doesn't define ("pending an ephemeral frame type", plan.md). Promote it to a named protocol-v2 deliverable so the divergence is a shipped fact rather than a comparative claim.

**N6 — Coverage checker production posture.** The checker is v1-required but only its dev-mode form is specified. Their model is structurally immune to the trap, so our residual production risk (post-deploy drift between channel and query selectors) deserves a stated posture — even if the answer is "dev-only, by design." Anchor: plan.md priors-audit #1, scenario-hobbyist (whatever the answer, it must cost the hobbyist nothing).

## 8. Sharpest Critique (their architect's voice)

"You wrote 'read-modify-write per update, with fn executing inside the transaction' and never said what *transaction* means when two of them run. That's not a missing paragraph, it's an undefined term in the middle of your write path. Under serializable semantics your hot document retries itself to death — you computed that math against *us*. Under last-write-wins interleave your own computed fields produce write skew — the stale-total bug ships in your schema layer, silently, which your taxonomy calls the one unforgivable failure. Every mechanism you've specified — the four-phase pipeline, computed derivations, id-addressed arrays — quietly assumes an isolation level you never named. We named ours and built a committer for it, because anything less than serializable is too hard a programming model — and the irony is your own aggregate-document principle hands you serializability at the only boundary your domain cares about, for the price of a row lock. You have the better data model for it and you still haven't written the sentence."
