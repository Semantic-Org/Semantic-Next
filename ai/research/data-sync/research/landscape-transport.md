# Transport 2026 — WS/SSE/long-poll, resumability, protocol lessons

2026 transport landscape for sync protocols: WebTransport reached Baseline in March 2026 (Safari 26.4 shipped it on macOS and iOS) but installed base (~85%) and server-side HTTP/3 ecosystem still lag, so it is an upgrade path, not a foundation. The field has split along a structural line: query-subscription engines (Zero, InstantDB, Convex, PowerSync) use WebSockets because they hold per-client query state anyway, while log-replication engines (Electric) use plain HTTP long-poll/SSE with offset-addressed URLs because a stateless read path lets CDNs do fan-out via request collapsing. Electric generalized this into Durable Streams (Dec 2025), an open HTTP protocol with opaque monotonic offsets, client-held progress, and no per-client server session state. The strongest 2026 recommendation for a new protocol: make cursor-based resumability the protocol core (not a transport feature), serve the read path over HTTP semantics (cacheable catch-up reads + long-poll/SSE live mode, with a defined cursor-expiry/snapshot-reset path learned from Postgres LSN retention), use a session transport (WebSocket/Durable Objects) only where per-client state is inherent, and keep pluggable: wire encoding (JSON default, binary opt-in), live-delivery mechanism (long-poll vs SSE vs WS, conformance-equal), storage backend, and fan-out infrastructure (CDN vs broker vs edge actor). DDP's failure modes — per-session mergebox memory, oplog tailing collapse, MongoDB coupling, unimplementable-elsewhere spec — and gRPC-web's trailer/proxy trap are the cautionary lessons baked into that recommendation.

## Findings

### WebTransport: Baseline as of March 2026, but not yet a sole-transport foundation

Safari 26.4 (macOS + iOS) shipped WebTransport in March 2026, making it Baseline across Chrome 97+, Edge 98+, Firefox 114+, Safari 26.4+ — confirmed on caniuse (https://caniuse.com/webtransport, global usage 85.48%) and https://webrtc.ventures/2026/04/webtransport-is-now-baseline-what-it-means-for-real-time-media/. Caveats: installed base lags API support (older iOS), MOQ application layer is pre-standardization ('a 2026-2027 adoption story'), server-side requires HTTP/3/QUIC termination and UDP through middleboxes, and fallback paths are still expected. Sources written earlier in 2026 still call it experimental: websocket.org's comparison (https://websocket.org/comparisons/) lists 75% support and says 'consider WebTransport for greenfield projects that can wait'; FlowVerify's April 2026 guide (https://www.flowverify.co/blog/sse-websockets-polling-guide-2026) claims it 'hasn't landed in Safari at all' — verifiably stale against caniuse. Net: viable to prototype, wrong to require. A new protocol should be framed transport-agnostically so WebTransport's independent streams (per-entity stream, no head-of-line blocking) can slot in later.

### WebSocket vs SSE in 2026: both production-grade, split by directionality and infrastructure

WebSockets: 99%+ support, mature, default for genuinely bidirectional interaction (https://websocket.org/comparisons/). SSE: ~97%, unidirectional, plain HTTP so it traverses corporate proxies, load balancers, CDNs, and API gateways with zero config, has built-in reconnection (Last-Event-ID), and is the consensus default for one-way push including LLM token streaming (https://www.flowverify.co/blog/sse-websockets-polling-guide-2026, https://rxdb.info/articles/websockets-sse-polling-webrtc-webtransport.html). The MCP ecosystem's move to Streamable HTTP — plain request that optionally upgrades to SSE only when streaming is needed — is the notable 2026 pattern for serverless/edge friendliness (https://www.buildmvpfast.com/blog/streaming-llm-responses-sse-vs-websockets-2026).

### Sync engine survey: transport choice tracks where per-client state lives

WebSocket camp (per-client query state on server): Zero/Rocicorp — persistent WebSocket to zero-cache, server reconciliation, Postgres logical replication into SQLite replica, 1.0 released June 8 2026 (https://zero.rocicorp.dev/docs/deployment, https://www.infoq.com/news/2026/06/zero-version-1/, https://marmelab.com/blog/2025/02/28/zero-sync-engine.html). InstantDB — WebSocket 'Reactor', InstaQL compiled to Datalog, server tails Postgres WAL to invalidate exactly the affected client queries, modeled on Asana WorldStore and Figma LiveGraph, persistent client outbox for offline writes (https://www.instantdb.com/essays/architecture). Convex — WebSocket, automatic query dependency tracking, server reruns affected queries and pushes deduplicated results (https://stack.convex.dev/how-convex-works, https://stack.convex.dev/object-sync-engine). PowerSync — supports both, WebSocket now default over HTTP streaming, JSON rows, schemaless protocol, checkpoint/write-checkpoint sequencing, interrupt-and-resume from last point (https://docs.powersync.com/architecture/powersync-protocol, https://github.com/powersync-ja/powersync-service/blob/main/docs/sync-protocol.md, https://powersync.com/blog/websockets-as-alternative-to-http-streaming-in-react-native). HTTP camp (stateless log read path): Electric — shapes (partial table replicas) exposed as append-only shape logs over GET with offset + shape handle, electric-offset header for pagination, live=true long-poll for tail, cache-control/etag for CDN caching, CDN request collapsing coalesces concurrent long-polls so 'millions of concurrent clients' hit the origin once per change (https://electric.ax/docs/api/http). The structural insight: if the server must hold per-client query state anyway, a socket session costs nothing extra; if the read path is a shared log, statelessness buys CDN fan-out and serverless compatibility.

### Resumability: opaque monotonic cursors with client-held progress is the converged design

Electric's Durable Streams (announced Dec 9 2025, 0.1.0 Dec 23 2025) generalizes the pattern into an open protocol: streams are addressable append-only logs readable from any position, offsets are opaque and monotonic, clients persist their own offset and reconnect with 'everything after X' — 'the server doesn't need per-client session state; the stream is durable, and progress is tracked client-side.' Offset-based URLs make historical reads CDN-cacheable. Layered design: byte-stream protocol below, a State Protocol above adding insert/update/delete on typed entities with optional txid, and conformance tests verifying 'SSE and long-poll produce identical results for the same stream and offset' (https://electric.ax/blog/2025/12/09/announcing-durable-streams, https://electric.ax/blog/2025/12/23/durable-streams-0.1.0). PowerSync resumes via checkpoints from the last synced point. The Postgres CDC ecosystem supplies the hard edge cases: consumers resume from confirmed_flush_lsn, slots pin WAL retention, and a client cursor older than the server's retention window must trigger a full re-snapshot rather than silent data loss — Debezium specifically fixed a data-loss path by resuming from last-flushed LSN instead of last-committed-transaction LSN (https://www.morling.dev/blog/postgres-replication-slots-confirmed-flush-lsn-vs-restart-lsn/, https://github.com/debezium/debezium/pull/1220). Protocol implication: cursor validity windows and an explicit reset-to-snapshot transition belong in the protocol, not as an error case.

### Serverless/edge WebSockets in 2026: solved on Cloudflare, still HTTP-shaped elsewhere

Cloudflare Durable Objects' WebSocket Hibernation API is GA: ctx.acceptWebSocket() marks sockets hibernatable, the DO is evicted from memory while connections stay open, duration billing stops during hibernation, and the runtime reconstructs the object on the next message — turning an idle connection from 'hold a process' into 'hold a row' and making DOs arguably the cheapest planet-scale WebSocket fan-out in 2026 (https://developers.cloudflare.com/durable-objects/best-practices/websockets/, https://callsphere.ai/blog/vw1c-cloudflare-durable-objects-websocket-fanout-hibernation). A 2026-04-07 compat flag (web_socket_auto_reply_to_close) cleaned up zombie CLOSING sockets. Outside Cloudflare, classic serverless (Vercel functions, Lambda) supports stable HTTP response streaming/SSE but not long-lived inbound WebSocket termination in-function — Vercel's streaming uses bridge code over Lambda precisely because the platform is request-shaped (https://vercel.com/blog/streaming-for-serverless-node-js-and-edge-runtimes-with-vercel-functions). This is a real deployment-surface argument for an HTTP-first read path: it runs everywhere, with WebSocket as an optimization where the platform supports it.

### Backpressure and fan-out patterns

Three fan-out architectures in production use: (1) broker-based — WebSocket gateways terminate connections and subscribe to Redis/NATS/Kafka channels, decoupling client concurrency from message production (https://medium.com/@bhagyarana80/top-10-websocket-fan-out-patterns-for-millions-of-rooms-6b0a9bd0f3ed); (2) CDN request collapsing — Electric's long-poll coalescing makes the CDN the fan-out layer with zero origin connections held (https://electric.ax/docs/api/http); (3) edge actors — Durable Objects with hibernation. Backpressure: WebSocket's only browser-side signal is bufferedAmount polling against a threshold; server-side, a small fraction of slow consumers can OOM a node holding per-connection send buffers, so bounded queues plus slow-consumer eviction are required practice (https://skylinecodes.substack.com/p/backpressure-in-websocket-streams, https://websockets.readthedocs.io/en/4.0.1/design.html). Note the asymmetry: HTTP pull (client requests next page from offset) gets backpressure for free since the client paces itself — push transports have to build flow control; pull transports inherit it.

### Protocol-design lessons: DDP retrospective

DDP's failure modes are the canonical anti-patterns. (1) Per-session server state: the mergebox keeps a per-client copy of each client's subscription data server-side — Meteor's own guide warns publications should return identical data across users, and one production app measured ~8MB per connected client (https://guide.meteor.com/performance-improvement, https://joshowens.dev/how-to-scale-a-meteor-js-app/). (2) Change-detection coupling: oplog tailing makes every app server process the entire database write stream, collapsing under batch writes — the community's Redis Oplog exists to route around it (https://forums.meteor.com/t/meteor-scaling-redis-oplog-status-prod-ready/30855/215, https://radekmie.dev/blog/on-oplog-replacement-in-meteor/). (3) Ecosystem closure: implementing DDP outside JS (Unity, Swift) required reverse-engineering and third-party clients 'so buggy that UX suffered' — tight MongoDB coupling and an implementation-defined spec killed portability (https://forums.meteor.com/t/replacement-for-ddp/61325, https://github.com/meteor/meteor/blob/devel/packages/ddp/DDP.md). (4) No resumability: reconnect means full re-subscribe. Extracted lessons: keep the read path stateless or cheap per client, decouple change detection from app servers, write a spec simple enough for a weekend port to another language, and make resume-from-cursor a first-class verb.

### Protocol-design lessons: gRPC-web and framing

gRPC-web: browsers can't read HTTP/2 trailers or control frames, so gRPC-web encodes trailers as flagged body messages, requires a proxy, and permanently lost client-streaming and bidirectional streaming — only unary and server-streaming are recommended (https://learn.microsoft.com/en-us/aspnet/core/grpc/grpcweb?view=aspnetcore-8.0, https://kreya.app/blog/grpc-web-deep-dive/). Lesson: never design above primitives the browser doesn't actually expose; fetch-with-streams, SSE, and WebSocket are the real substrate. JSON vs binary: protobuf is ~30-50% smaller than JSON with 47-80% higher message throughput and 18-44% less CPU/memory in WebSocket benchmarks (https://hjkl11.hashnode.dev/performance-analysis-of-json-buffer-custom-binary-protocol-protobuf-and-messagepack-for-websockets), yet Electric, PowerSync (explicitly 'data for individual rows are represented using JSON', schemaless by design), and most sync engines ship JSON — debuggability, CDN/proxy transparency, and zero-schema client portability dominate at sync-protocol message sizes. Centrifugo's dual JSON/Protobuf framing shows encoding can be a negotiated layer rather than a protocol commitment (https://centrifugal.dev/docs/transports/websocket). Braid-HTTP (IETF draft-toomim-httpbis-braid-http: versioning + patches + subscriptions + 209 status) validates the HTTP-native sync direction but its draft expired March 2024 without standardization — don't wait for it, but its layering (versions, patches, subscriptions as orthogonal extensions) is good prior art (https://datatracker.ietf.org/doc/html/draft-toomim-httpbis-braid-http).

### Recommendation: what a new 2026 sync protocol should choose

TRANSPORT: HTTP-first read path — offset-addressed catch-up reads (cacheable GETs) plus a live mode deliverable over either long-poll or SSE with conformance-identical results (Electric/Durable Streams pattern). This gets CDN fan-out, serverless/edge deployability, proxy traversal, and free pull-based backpressure. Use a stateful session transport (WebSocket, or Durable Objects on Cloudflare) only for surfaces where per-client state is inherent: live query subscriptions with server-side reconciliation, presence, or high-frequency client-to-server writes. Writes go over plain HTTP POST regardless — every surveyed engine separates the write path from the sync stream. RESUMABILITY: protocol core, not transport feature — opaque monotonic cursors, progress held client-side, server stateless on read, plus an explicit cursor-expiry/snapshot-reset transition (the LSN retention lesson) so falling off the log's retention window is a defined protocol state, not an error. KEEP PLUGGABLE: (1) wire encoding — JSON default for debuggability and CDN transparency, binary (protobuf/MessagePack) as negotiated opt-in; (2) live-delivery mechanism — long-poll/SSE/WebSocket/future-WebTransport behind one stream abstraction, since WebTransport's Baseline status (March 2026) makes it a plausible 2027 upgrade but not a 2026 requirement; (3) storage/change-capture backend — don't repeat DDP's MongoDB coupling, define the log contract and let Postgres-WAL/SQLite/anything implement it; (4) fan-out infrastructure — CDN collapsing vs broker pub/sub vs edge actors are deployment choices the protocol should not see; (5) auth — header/proxy-based, outside the protocol (Electric's gatekeeper pattern). DELIBERATELY FIX (not pluggable): cursor semantics, ordering guarantees, the catch-up/live state machine, and the reset path — these are the interoperability surface, and a spec simple enough to port in a weekend is the anti-DDP portability test.
