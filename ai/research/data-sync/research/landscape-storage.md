# Client storage 2026 — IndexedDB, OPFS/SQLite, multi-tab, quotas

For app-data-scale (tens of MB, not GB) sync-engine workloads in 2026, the production consensus is memory-first with IndexedDB write-behind: Zero 1.0 (June 2026) defaults to kvStore:'idb' built on Replicache's in-memory lazy b-tree that persists every few seconds, Linear hydrates an in-memory MobX object pool from IDB with a durably-persisted mutation queue, and LiveStore runs in-memory SQLite with worker-side OPFS persistence. IndexedDB's bottleneck is per-transaction overhead (~80ms for 1000 docs in one tx vs ~2s as 1000 txs), not throughput, and Chrome 121 (Jan 2024) made relaxed durability the default, so batched IDB is fast enough when reads come from memory. OPFS-SQLite (wa-sqlite OPFSCoopSyncVFS or official opfs-sahpool, neither requiring COOP/COEP) is mature and ~4x faster for bulk I/O but costs ~940KB of wasm, ~500ms init, worker plumbing, a single-writer multi-tab protocol (Notion needed SharedWorker brokering after real corruption), and Safari/Android fallbacks — justified for 100MB+ relational data and client-side SQL, not for app-data K/V. Multi-tab coordination should use Web Locks leader election (Baseline since March 2022) + BroadcastChannel, because SharedWorker is still unsupported on Chrome for Android as of v148 and OPFS sync handles can't live in a SharedWorker anyway. Always request navigator.storage.persist() — Safari still evicts non-interacted origins after 7 days, and eviction wipes IDB+OPFS+Cache together.

## Findings

### IndexedDB performance: transaction commit overhead dominates, not throughput

RxDB measurements (rxdb.info/slow-indexeddb.html): inserting 1,000 documents in ONE transaction takes ~80ms (0.08ms/doc); the same writes as one-transaction-each takes ~2s (~25x worse). Document size barely affects write speed — transaction setup/commit is the bottleneck. Nolan Lawson (nolanlawson.com, canonical IDB perf reference): each cursor.continue() is a main-thread<->IDB-engine round trip creating separate JS tasks; replacing cursors with batched getAll()/getAllKeys() improved reads 40-50% (Safari: 4,673ms -> 227ms for 50k records, batch size 100). Explicit transaction.commit() gains are negligible ('squint to see'). Per-op numbers from RxDB's 2024+ comparison article: small write IDB 0.17ms vs localStorage 0.017ms; 200-doc bulk write IDB 13.41ms; IDB init 46ms. New getAllRecords() API (2025) improves bulk-read ergonomics. Practical recipe: few large transactions, getAll batching, optional store sharding (~28-43% gains).

### Relaxed durability is now the default (Chrome 121, Jan 2024)

Chrome 121 changed IndexedDB default durability from 'strict' to 'relaxed' (developer.chrome.com/blog/indexeddb-durability-mode-now-defaults-to-relaxed), aligning with Firefox and Safari which never fsync'd per-commit. Relaxed mode skips explicit OS flush; the complete event fires once data reaches the OS buffer (flushed every couple of seconds). Impact: up to 10x+ on flush-heavy add benchmarks (chromestatus.com/feature/5730701489995776), 17-27% on large single transactions, dramatic on many small transactions (Nolan Lawson: 1,000 one-item transactions 1,074.6ms -> 65.4ms). Implication for 2026: explicitly setting {durability:'relaxed'} is now mostly redundant on Chrome; the historical 'IndexedDB is slow because Chrome fsyncs' complaint is fixed. Data-loss window on power failure is seconds of OS buffer — acceptable for a sync engine where server is source of truth.

### Structured clone cost: serialization happens synchronously on the writing thread

IndexedDB stores values via the structured clone algorithm — the copy is made at put() time on the calling thread, so large object graphs block the main thread proportionally to size (MDN structured clone docs; javascript.info/indexeddb). Mitigations: smaller atomic records, ArrayBuffer payloads (near-zero clone cost), or doing writes from a worker so cloning happens off the UI thread (cloning into the worker via postMessage is itself a structured clone, but it amortizes). This is a second argument for write-behind: snapshotting from memory to IDB in idle periods keeps clone cost out of interaction latency. No single canonical 2024+ benchmark exists for clone cost; treat as size-proportional main-thread blocking.

### Safari/WebKit realities: 7-day eviction, periodic data-wipe bugs, OPFS gaps in private browsing

(1) Safari deletes ALL script-writable storage (IDB, localStorage, OPFS, Cache API) for origins with no user interaction in 7 days — still active policy per MDN storage quotas page and webkit.org/blog/14403/updates-to-storage-policy. Installed-to-homescreen PWAs are exempt. (2) WebKit bug 266559 (filed late 2023, reports through 2024): Safari periodically erasing localStorage AND IndexedDB for all websites. (3) Long history of iOS IDB flakiness: transaction hangs, post-OS-update data loss, unbounded storage usage (WebKit bug 178204), summarized in pesterhazy's 'pain and anguish of IndexedDB' gist. (4) Safari private browsing lacks OPFS sync access handles entirely — PowerSync's May 2026 report says an IndexedDB-VFS fallback is required there, and wa-sqlite's IDBBatchAtomicVFS hits 'stack size exceeded' on Safari with large queries. Net: on WebKit, treat ALL client storage as a cache that can vanish, design for full resync.

### SQLite WASM + OPFS maturity (May 2026 state)

Per PowerSync's 'SQLite Persistence on the Web: May 2026 Update' and sqlite.org/wasm/doc/trunk/persistence.md, four viable VFS families: (1) wa-sqlite OPFSCoopSyncVFS — recommended general-purpose since early 2025: no Asyncify/JSPI, no COOP/COEP, multi-tab via one connection per tab with cooperative locking, Chrome 108+/Safari 16.4+/Firefox 111+, holds performance past 1GB databases. (2) Official sqlite-wasm 'opfs-sahpool' (SQLite 3.43+) — highest OPFS performance, no COOP/COEP, but strictly single connection (second tab fails without external pause/unpause brokering). (3) Official 'opfs' VFS — the only one requiring COOP/COEP headers + SharedArrayBuffer + worker; multi-tab works but contends with SQLITE_BUSY. (4) wa-sqlite IDBBatchAtomicVFS — IndexedDB-backed for old browsers/Safari-incognito; needs Asyncify (~2x wasm size, 2-5x slower) or JSPI (Chrome 137+ unflagged, Firefox behind flag); degrades badly at 100MB+. New April 2026: OPFSWriteAheadVFS, first VFS with concurrent reads during writes, Chrome 121+ only. Costs: official sqlite3.wasm ~938.9KB uncompressed (RxDB), ~500ms init for WASM-SQLite-on-IDB vs 46ms for raw IDB; Chrome incognito caps DBs at 100MB; OPFS sync handles unavailable inside SharedWorkers (dedicated workers only).

### COOP/COEP is effectively avoidable now — and Notion proved why you want to avoid it

Only the official 'opfs' VFS needs cross-origin isolation; OPFSCoopSyncVFS and opfs-sahpool don't. Notion (July 2024, notion.com blog) chose the OPFS SyncAccessHandle Pool VFS specifically because COOP/COEP 'would have prevented rolling out to any browser beyond Chrome and Edge' — third-party iframe vendors couldn't comply ('an unrealistic ask'). Results: 20% faster page navigation overall, 28-33% in Australia/China/India. Hard lessons: multiple tabs writing concurrently CORRUPTED SQLite (duplicate row IDs, wrong page data) — fixed with a SharedWorker that elects one 'active tab' writer, each tab having its own dedicated worker, tab-death detected via Web Locks release; slow-disk mobile devices regressed at p95 — fixed by racing SQLite reads against API requests; wasm load initially blocked page load — made fully async.

### What production sync engines actually chose

Zero (Rocicorp, 1.0 shipped June 8 2026 per InfoQ): kvStore option defaults to 'idb' — verified in source (rocicorp/mono packages/zero-client/src/client/options.ts: "Defaults to 'idb'... persisted on the client and enables faster syncs between application restarts"; get-kv-store-provider.ts maps undefined -> newIDBStoreWithMemFallback). Built on Replicache's storage: in-memory versioned b+tree reads at memory speed, lazily persists every few seconds to IDB, new clients fork prior instance state. Boodman frames the client store as 'just a fancy cache'; offline writes are explicitly unsupported (zero.rocicorp.dev/docs/offline). Client bundle 232KB gzipped — no wasm. PowerSync: wa-sqlite, IDBBatchAtomicVFS default for compatibility, OPFS variants opt-in (OPFSCoopSyncVFS recommended, esp. Safari/multi-tab; AccessHandlePoolVFS single-tab; OPFSWriteAheadVFS Chromium read-heavy); multi-tab via SharedWorkers + Web Locks (also used to stop Chrome/Edge tab-freezing from suspending the DB); multi-tab unavailable on Android. LiveStore (0.4.x, 2025-2026): event-sourced; in-memory SQLite on the main thread for synchronous reads, persistence via worker using a wa-sqlite fork on OPFS AccessHandlePoolVFS, WAL disabled as unreliable on that VFS; open issue #321 on Chrome-Android SharedWorker gap. Linear (reverse-engineered, endorsed by CTO — wzhudev/reverse-linear-sync-engine): in-memory MobX object pool hydrated from IndexedDB, UI reads memory only, mutations apply to MobX + durable transaction queue in IDB + server queue simultaneously; heavy tables (Issue, Comment) lazy-hydrate. TanStack DB (Nov 2025, issue #865): in-memory-first today, persistence layer still in design — requirements list pluggable IDB/OPFS/SQLite backends, multi-tab safety, schema versioning, larger-than-memory paging.

### Memory-first + write-behind vs storage-first

Memory-first (Replicache/Zero, Linear, LiveStore, RxDB memory-synced storage): reads are synchronous and ~100x faster than IDB ops (RxDB), zero transaction overhead and zero structured-clone on the hot path, enables fine-grained reactivity. Persistence happens on idle/interval/unload. The critical correctness split: the PENDING MUTATION QUEUE must be flushed durably and eagerly (Linear writes it to IDB at mutation time; Replicache persists frequently), while the synced-data SNAPSHOT can be lazy because it's reconstructible from the server — losing seconds of snapshot just means re-syncing. Costs: leader election adds ~150ms startup (RxDB), crash-before-flush loses unflushed local-only state, memory ceiling caps dataset size. Storage-first (PowerSync, Notion): SQLite in a worker is the source of truth — survives larger-than-memory data, real SQL with indexes/joins, ACID locally, but every read crosses a worker boundary (async, no sync reads) and you inherit the wasm/VFS/multi-tab machinery. For app-data scale the memory ceiling is irrelevant, which removes storage-first's main structural advantage.

### Storage quotas and navigator.storage.persist() (2026)

Per MDN 'Storage quotas and eviction criteria': Chrome/Edge — up to 60% of disk per origin (best-effort AND persistent), browser-wide cap ~80%; Chrome incognito ~100MB SQLite-DB ceiling (PowerSync). Firefox — best-effort min(10% of disk, 10GiB eTLD+1 group limit); persistent mode 50% of disk, no group limit. Safari — ~60% of disk for browser apps, ~15% in embedded WebViews, cross-origin frames get ~1/10 of parent quota, plus the 7-day no-interaction eviction. navigator.storage.persist(): Firefox shows a permission prompt; Chrome/Edge/Safari silently auto-grant/deny based on engagement heuristics (installed PWA, bookmarks, high site engagement). Eviction is all-or-nothing per origin: IDB + Cache API + OPFS are wiped together to avoid cross-store inconsistency. Practical guidance: call persist() early, check navigator.storage.estimate(), catch QuotaExceededError, and still design for total loss on WebKit.

### Multi-tab coordination: Web Locks leader election is the portable primitive; SharedWorker still missing on Android Chrome

SharedWorker support (caniuse.com/sharedworkers, checked June 2026): Chrome for Android NOT supported through v148 — the only major browser missing it (chromestatus feature 6265472244514816 remains unshipped, long-standing blink-dev thread); Safari re-added it in 16.0 (after being absent 6.1-15.8); Firefox Android supports it. Consequences in production: PowerSync's multi-tab mode 'currently unavailable on Android'; LiveStore issue #321 tracks the same gap. Web Locks API: Baseline Widely Available since March 2022 (MDN), exclusive held-forever lock + queued waiters is the documented leader-election pattern; used by PowerSync (also to prevent Chrome tab-freezing from suspending DB connections) and Notion (lock release = tab closed). BroadcastChannel: universally available, used for cross-tab cache invalidation / log broadcast. Additional constraint pushing the same design: OPFS sync access handles cannot be used inside a SharedWorker, so even where SharedWorker exists it can only broker, not own, the database — the robust portable architecture is dedicated worker per tab + Web Locks leader election + BroadcastChannel fan-out, with the leader owning storage writes.

### Decision matrix for an app-data-scale sync engine client

PLAIN INDEXEDDB (batched, relaxed durability) is right when: dataset is small-to-moderate (single-digit-to-low-hundreds MB), the sync engine ships its own query/index layer over a K/V or document model, bundle size matters (0KB vs ~940KB wasm), you don't control response headers, you need Android Chrome multi-tab, and startup must be fast (46ms vs ~500ms init). This is exactly Zero/Replicache's choice. MEMORY + WRITE-BEHIND (over IDB) is the strongest default for a sync engine at this scale: synchronous reads for reactivity, IDB demoted to a snapshot + durable mutation queue, full-resync as the recovery story — the Zero/Linear/LiveStore convergence. Pair with Web Locks leader election for who persists. OPFS-SQLITE is right when: you need genuine client-side SQL (ad-hoc joins/aggregations the engine can't precompute), databases at 100MB-1GB+ where IDB and IDB-backed VFSs degrade, or larger-than-memory paging; choose wa-sqlite OPFSCoopSyncVFS (multi-tab, no headers) or opfs-sahpool + single-writer brokering, keep an IDB-VFS fallback for Safari private browsing, and accept the Android multi-tab gap. AVOID: the COOP/COEP 'opfs' VFS unless you fully control headers and embed no third-party iframes; treating any of this as durable storage on WebKit. For gigabyte-scale document workloads (Notion) storage-first OPFS-SQLite wins; for app-data workloads the evidence says IndexedDB with an in-memory layer wins on simplicity, startup, compatibility, and bundle size.
