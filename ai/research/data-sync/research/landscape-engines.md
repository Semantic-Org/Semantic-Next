# 2026 sync engines — Zero, Electric, PowerSync, Instant, convergent patterns

Survey of 11 local-first/sync-engine systems as of June 2026, with per-system data on storage, transport, partial sync, conflict strategy, write path, and backend coupling. Headline status changes verified against primary sources: Zero hit 1.0 (June 8, 2026), Replicache is in maintenance mode, Triplit was acqui-hired by Supabase (Oct 8, 2025) and is community-maintained, ElectricSQL repositioned as an "agent platform" on a new electric.ax domain, LiveStore is beta v0.4, Jazz shipped a v2 alpha repositioned as a "local-first relational database," Automerge 3.0 (July 2025) cut memory 10x+, TanStack DB shipped 0.5 query-driven sync (March 2026), and Jamsocket (y-sweet/Yjs hosting) is shutting down into Modal Labs. Convergence: server-authoritative mutator rebase ("server reconciliation") has won for app data with CRDTs relegated to embedded document/text collaboration, queries-as-subscriptions is displacing static shapes/buckets as the partial-sync model, IVM/differential dataflow is table stakes for live queries, Postgres logical replication is the standard source of truth, and the field has retreated from full offline-writes toward online-first optimistic caches.

## Findings

### Rocicorp Zero — 1.0 shipped June 8, 2026

STATUS: 1.0 released June 8, 2026 after ~2 years / 50+ releases (infoq.com/news/2026/06/zero-version-1). (a) STORAGE: client-side store of recently-used rows persisted to IndexedDB (zero-client lineage from Replicache); positioned as 'just a fancy cache' that cannot corrupt data; 718KB bundle (232KB gzip). (b) TRANSPORT: WebSocket between zero-client and zero-cache; zero-cache tails Postgres logical replication. (c) PARTIAL SYNC: queries-as-subscriptions via ZQL 'synced queries' — query runs locally first, name+args sent to zero-cache which fetches ZQL from your server's queries endpoint; client replica is the union of all active queries' results; TTL-based lifecycle (default 5m) keeps deactivated queries warm. (d) CONFLICT: server reconciliation ('pioneered by the video game industry') — optimistic writes rebased on canonical server history. Explicitly NO offline writes: 'when disconnected... writes are rejected and return an offline error'; docs recommend blocking user input while disconnected. (e) WRITE PATH: named custom mutators, client implementation for optimistic apply + server implementation as authority. (f) COUPLING: Postgres only (no views, no array columns yet); requires running zero-cache service (self-hostable) plus your own API server for queries/mutators endpoints.

### Replicache — maintenance mode, free and open-sourced

STATUS: maintenance mode after 5 years: 'We will continue to support Replicache, but won't add new features'; code open-sourced, no longer charged for; users directed to migrate to Zero (replicache.dev). (a) STORAGE: IndexedDB in browser. (b) TRANSPORT: HTTP push/pull endpoints you implement on your backend, plus a 'poke' hint channel for realtime. (c) PARTIAL SYNC: your pull endpoint computes the per-client view — entirely backend-defined, no query language. (d) CONFLICT: 'a form of server reconciliation — an intuitive and powerful technique from multiplayer games' — speculative mutations replayed/rebased atop authoritative server state. (e) WRITE PATH: named mutators with client + server implementations. (f) COUPLING: backend-agnostic — any stack that can implement push/pull. Historical note: Rocicorp's middle product Reflect was retired (servers off November 1, 2024; users pointed at Liveblocks) to focus on Zero (rocicorp.dev/blog/retiring-reflect).

### ElectricSQL — read-path-only shapes; rebranded as 'agent platform' on electric.ax

STATUS: major repositioning in 2026 — electric-sql.com now 301-redirects to electric.ax, homepage reads 'Electric is the first agent platform built on sync' with products Electric Agents, Electric Streams, Electric Sync, Electric Cloud ('1M+ concurrent readers' via CDN). The sync engine is now the substrate, agents the pitch. (a) STORAGE: unopinionated — in-memory via useShape, or materialize into PGlite or TanStack DB collections. (b) TRANSPORT: HTTP long-polling against GET /v1/shape (offset=-1 initial, live=true for updates), shape-log semantics, CDN-friendly fan-out. (c) PARTIAL SYNC: Shapes — single-table + where clause + column selection; subquery filtering (id IN (SELECT...)) in preview; NO joins ('Shapes sync data from a single table'), multiple shapes needed for related data. (d) CONFLICT: none — read path only. (e) WRITE PATH: explicitly none: 'Electric does not do write-path sync. It doesn't provide (or prescribe) a built-in solution for getting data back into Postgres.' Four documented patterns: online writes, optimistic state, shared persistent optimistic state, through-the-database sync. (f) COUPLING: Postgres with logical replication; Electric is an Elixir service between API and DB; Apache 2.0, open HTTP protocol. Community opinion divided — one 2026 comparison (johnny.sh) calls long-polling 'an extremely slow and brittle technique' and is hostile to the project, while it anchors TanStack DB's flagship collection.

### PowerSync — SQLite replica, bucket/stream partial sync, backend-authoritative writes

STATUS: active and commercial with self-hostable service; evolving from classic Sync Rules to Sync Streams; shipped query-driven sync for its TanStack DB collection March 25, 2026 (releases.powersync.com). (a) STORAGE: client-side SQLite — schemaless JSON in ps_data__<table> with SQLite views over it, plus ps_oplog; checkpoint system copies oplog to tables only when a full checkpoint downloads (consistency guarantee). (b) TRANSPORT: 'either HTTP streams or WebSockets (depending on the specific Client SDK).' (c) PARTIAL SYNC: declarative Sync Rules defining Sync Buckets (parameter+data queries; every bucket parameter must appear in every data query), newer Sync Streams; buckets may overlap. (d) CONFLICT: developer's backend is authoritative; default 'essentially last write wins,' customizable; recommended semantics: 'Deletes always win,' per-field LWW for concurrent updates; server-side validation allowed; CRDT data (Yjs) can be synced through it for collaborative text. (e) WRITE PATH: direct writes to local SQLite, auto-captured into a blocking FIFO upload queue of idempotent PUT/PATCH/DELETE ops with per-client incrementing IDs; your uploadData() implementation calls your own backend API — business logic/authz live there. No named mutators. (f) COUPLING: source databases Postgres, MongoDB, MySQL, SQL Server; requires PowerSync Service (hosted or self-host) plus your own write API.

### Triplit — acqui-hired by Supabase Oct 2025, now community-maintained

STATUS: Triplit 1.0 shipped March 2025 ('10-100X the performance', triplit.dev/blog/triplit-1.0); Supabase announced the acquisition October 8, 2025 (supabase.com/blog/triplit-joins-supabase) — founder Matt Linkous leads third-party integrations at Supabase, Triplit is NOT being integrated into the platform and moves to community maintenance with further open-sourcing. 2026 sync-engine roundups list it as effectively abandoned for new projects. (a) STORAGE: pluggable — IndexedDB, SQLite, Durable Objects, LevelDB, memory. (b) TRANSPORT: WebSockets. (c) PARTIAL SYNC: client query subscriptions ('a full-stack, syncing database... syncs over websockets'). (d) CONFLICT: CRDT-based with 'conflict resolution at the property level' (attribute-level LWW with logical clocks). (e) WRITE PATH: direct client inserts/updates through the database API — no named mutators. (f) COUPLING: requires Triplit's own Node sync server (self-hostable, fully open source). Notable as the field's main CRDT-for-app-data entrant — and the one that exited.

### InstantDB — triple store + InstaQL subscriptions, repositioned for AI-coded apps

STATUS: active; GitHub tagline now 'Instant is the best backend for AI-coded apps' — 2026 positioning is LLM-first app building (github.com/instantdb/instant). (a) STORAGE: client-side immutable triple store ([entity, attribute, value] tuples, Mutative for immutable updates) persisted to IndexedDB (web) / AsyncStorage (React Native). (b) TRANSPORT: WebSockets — the 'Reactor' client state machine sends queries+transactions, receives 'results and novelty.' (c) PARTIAL SYNC: InstaQL (GraphQL-like JS-object relational queries) as live subscriptions; server tails the Postgres WAL to detect novelty and invalidate affected queries (explicitly inspired by Asana's WorldStore and Figma's LiveGraph). (d) CONFLICT: server-authoritative with optimistic apply — pending mutation queue; 'If the server returns a failure, we simply remove the change from the pending queue and undo works out of the box.' (e) WRITE PATH: db.transact(db.tx.todos[id()].update({...})) — transactional tx-chunk ops with server-enforced permissions; not named mutators. (f) COUPLING: their Clojure sync server + one multi-tenant Postgres ('All the data lives in a single triples table... logically isolated by app_id'); fully open source and self-hostable (instantdb.com/essays/architecture).

### LiveStore — event-sourced reactive SQLite, beta v0.4, no partial sync

STATUS: beta; launched publicly May 2025, current v0.4 ('Reworked sync transport + StoreRegistry'); built by Johannes Schickling (Prisma founder) for Overtone (livestore.dev, github.com/livestorejs/livestore). (a) STORAGE: embedded reactive SQLite kept up to date via materializers and persisted to device storage, plus a persisted eventlog — SQLite state is derived, events are the source of truth. (b) TRANSPORT: pluggable sync providers — Cloudflare (Workers/Durable Objects), ElectricSQL, S2, 'or roll your own'; git-style push/pull. (c) PARTIAL SYNC: none within a store — the whole eventlog syncs; partitioning happens by store instance (roughly one SQLite/eventlog per user or workspace), which 2026 reviewers flag as 'a big limitation when it comes to sharing data between users.' (d) CONFLICT: git-inspired rebase — 'Upstream events always need to be pulled before a client can push... Local pending events... need to be rebased on top of the latest upstream events,' preserving a global total order; deterministic materializers; custom merge conflict resolution supported. Offline writes fully supported. (e) WRITE PATH: named, typed events via store.commit(events.todoCompleted(id)) materialized to SQL — event sourcing, the closest cousin to named mutators. (f) COUPLING: backend is a dumb ordered event store; any provider implementing the sync protocol works.

### Convex — reactive database with queries-as-subscriptions; local-first as 'object sync engine'

STATUS: active; backend open source under FSL-Apache-2.0 (converts to Apache 2.0 after 2 years), self-hostable via Docker backed by SQLite or any Postgres (github.com/get-convex/convex-backend). (a) STORAGE: standard client keeps an in-memory cache of subscribed query results; the local-first 'object sync engine' design (stack.convex.dev/object-sync-engine) adds a persistent local store — IndexedDB now, SQLite planned. (b) TRANSPORT: WebSocket — 'syncs a set of queries and coordinates sending mutations from the client to the server.' (c) PARTIAL SYNC: queries-as-subscriptions over server-side deterministic query functions ('first-class support for executing a query and efficiently subscribing to its changes'); local-first variant runs JS queries against ctx.localDb. (d) CONFLICT: server-authoritative — mutations execute as serializable OCC transactions on the server; client optimistic updates applied via server reconciliation. (e) WRITE PATH: named server mutation functions, optionally paired with a local optimistic implementation (localMutation({ server: api.friends.addFriend, local: ... })) — the purest named-mutator design in the field. (f) COUPLING: requires the Convex platform (database + function runtime are inseparable from the sync protocol); also publishes guidance for layering Automerge CRDT docs on top for offline/collab cases (stack.convex.dev/automerge-and-convex).

### Jazz — CRDT-native, but v2 alpha pivots to 'local-first relational database' with queries

STATUS: active; v2 alpha announced (current as of 2026) repositioning Jazz from a CoValue/CRDT framework to 'a local-first relational database' with 'row-level security and per-query auth' — classic v1 still available (jazz.tools). (a) STORAGE: browser uses OPFS via a dedicated worker with cross-tab leader election; SQLite on native and for the self-hosted sync server (--db flag). (b) TRANSPORT: WebSocket to a sync server — Jazz Cloud (global) or 'the single-tenant Jazz database server will always be open-source and is very easy to self-host.' (c) PARTIAL SYNC: v1 loads CoValues granularly on demand along the reference graph; v2 sends query subscriptions upstream where the server evaluates them against its relational state — 'Sync partial tables, durable streams and files.' (d) CONFLICT: CRDTs — CoValues (CoMap, CoList, co.plainText/co.richText) keep full edit history and are eventually consistent; every row gets 'a full git-like branching history'; v2 adds optional globally-consistent transactions where eventual consistency isn't acceptable; E2E encryption with verifiable permissions throughout. Offline writes fully supported, queued and replayed on reconnect. (e) WRITE PATH: direct mutation of collaborative values — no named mutators. (f) COUPLING: Jazz IS the database (no separate Postgres); requires Jazz sync/storage server, cloud or self-hosted.

### TanStack DB — reactive client store over any backend; 0.5 query-driven sync (March 2026)

STATUS: launched 2025 as 'the reactive client store for your API'; 0.5 'Query-Driven Sync' shipped ~March 2026 (tanstack.com/blog/tanstack-db-0.5-query-driven-sync). Not a sync engine itself — a normalization layer above them. (a) STORAGE: in-memory typed collections (LocalOnlyCollection, LocalStorageCollection); durable persistence delegated to the backing adapter — QueryCollection (REST via TanStack Query), ElectricSQL shapes, PowerSync SQLite, RxDB, TrailBase. (b) TRANSPORT: whatever the collection adapter uses (HTTP polling/fetch, Electric long-poll shape log, PowerSync protocol). (c) PARTIAL SYNC: live queries compiled to differential dataflow (d2ts) — joins/filters/aggregates maintained incrementally ('Updating one row in a sorted 100,000-item collection completes in ~0.7ms'); three sync modes: eager (whole collection), on-demand (only rows active live queries need), progressive. (d) CONFLICT: optimistic overlay kept separate from synced state — 'If the handler throws an error, the optimistic state is rolled back'; authority belongs to your backend/sync engine (server-authoritative shape). (e) WRITE PATH: collection.insert/update/delete fire onInsert/onUpdate/onDelete handlers responsible for persisting to your backend; explicit transaction objects with lifecycle. (f) COUPLING: deliberately none — mixes REST, Electric, PowerSync, custom adapters in one app.

### Automerge / Yjs — CRDT libraries healthy but niche; Automerge 3.0 fixed memory, Jamsocket exited

AUTOMERGE: 3.0 released July 2025 (automerge.org/blog/automerge-3) — runtime now uses the compressed columnar representation, cutting memory 10x+ ('pasting Moby Dick... consumes 700Mb in Automerge 2, only 1.3Mb in Automerge 3'); full change history retained; actively maintained (Ink & Switch lineage). (a) storage via automerge-repo adapters (IndexedDB, fs); (b) transport via pluggable network adapters + a simple WebSocket sync-server (github.com/automerge/sync-server); (c) partial sync is per-document only — no queries; (d) conflict: CRDT merge with full history; (e) writes: direct mutation of the document via change functions; (f) backend-agnostic, servers optional. YJS: mature and widely embedded via editor bindings; lighter than Automerge, more integrations. Ecosystem event: Jamsocket — the company behind y-sweet (S3-backed Yjs document server) and learn.yjs.dev — is shutting down, with the team joining Modal Labs (jamsocket.com homepage: 'Jamsocket is shutting down'); y-sweet survives as MIT open source (last release Jan 2026) but loses its commercial host. Pattern: CRDT libs are now mostly consumed as embedded document/text-collaboration components INSIDE app-data sync systems (PowerSync syncs Yjs docs, Convex publishes an Automerge integration) rather than as whole-app data layers.

### CONVERGENT PATTERN 1 — server-authoritative mutator rebase won for app data; CRDTs relegated to documents

By mid-2026 the dominant conflict model for application data is server reconciliation: optimistic client writes replayed/rebased against an authoritative server. Zero (explicit 'server reconciliation'), Replicache (same lineage), Convex (OCC transactions + localMutation reconciliation), InstantDB (pending queue, failed tx undone), TanStack DB (optimistic overlay rolled back on handler error), PowerSync (developer backend authoritative, default LWW), and LiveStore (git-style event rebase against a totally-ordered upstream log) all place authority centrally. Pure-CRDT app-data plays retreated: Triplit (property-level CRDT) was acqui-hired into community maintenance; Jazz — the strongest CRDT-native framework — pivoted in v2 to a relational model with server-evaluated query subscriptions and optional globally-consistent transactions. CRDTs persist where they're genuinely needed: collaborative text/documents, embedded inside server-authoritative systems (PowerSync+Yjs, Convex+Automerge). Zero's docs make the argument explicit: offline concurrent edits to shared app data create 'unsolvable conflicts,' so they reject offline writes entirely.

### CONVERGENT PATTERN 2 — queries-as-subscriptions is displacing static shapes/buckets as the partial-sync model

The field converged on 'what you query is what syncs.' Zero synced queries (client replica = union of active ZQL query results, TTL lifecycle), InstantDB InstaQL live queries, Convex query-function subscriptions, Jazz v2 query subscriptions evaluated server-side, and TanStack DB 0.5's on-demand mode ('the collection only loads the rows your active live queries need') all derive the synced subset dynamically from live queries. The older declarative alternatives — PowerSync Sync Rules/Buckets and Electric Shapes (single-table where-clauses) — are both visibly migrating toward the query-driven model: PowerSync introduced Sync Streams and shipped query-driven sync for its TanStack DB collection (March 2026), and Electric's primary client-side story is now feeding TanStack DB live queries. Nobody new ships full-replica sync for multi-user app data; LiveStore is the exception (full eventlog per store) and works around it by partitioning stores per user/workspace.

### CONVERGENT PATTERN 3 — IVM/differential dataflow, Postgres substrate, and the SQLite-vs-IndexedDB client split

Incremental view maintenance is table stakes: Zero's ZQL 'maintains results incrementally as data changes,' TanStack DB compiles live queries to differential dataflow (d2ts), Electric evaluates shape where-clauses incrementally against the logical replication stream, InstantDB tails the WAL to invalidate exactly the affected queries (WorldStore/LiveGraph lineage), Convex re-runs deterministic query functions with read-set-based invalidation. Re-running queries from scratch is now disqualifying. Beneath it, Postgres logical replication/WAL-tailing is the de facto source-of-truth interface (Zero, Electric, PowerSync's primary path, InstantDB's storage, Convex self-host option), with PowerSync the outlier in also supporting MongoDB/MySQL/SQL Server. On the client there's a clean two-camp split: durable SQLite replicas (PowerSync ps_data tables, LiveStore materialized SQLite, Jazz v2 OPFS-backed relational DB) for offline-capable apps vs IndexedDB/in-memory caches (Zero, Replicache, InstantDB triple store, Convex, TanStack DB) for online-first apps — and the cache camp explicitly accepts dropped offline writes as a feature, not a gap.

### CONVERGENT PATTERN 4 — unbundling of read path from write path, and the 2026 agent repositioning wave

Architecture unbundled into composable layers: read-path replication (Electric: 'Electric does read-path sync... does not do write-path sync'), client-side reactive store (TanStack DB, layerable over Electric/PowerSync/REST/RxDB/TrailBase), and write path through your own API (Electric's four write patterns, PowerSync's uploadData() connector, TanStack DB's onInsert/onUpdate handlers). Write-path styles split into named mutators/events (Zero, Replicache, Convex, LiveStore events) vs direct writes captured automatically (PowerSync SQLite capture, Triplit, Jazz, InstantDB transact) — but in every surviving system the server retains a hook for business logic and authorization. Separately, 2025-2026 brought an AI repositioning wave: ElectricSQL relaunched as 'the first agent platform built on sync' (Electric Agents/Streams on electric.ax), InstantDB rebranded as 'the best backend for AI-coded apps,' and Convex markets agent-ready reactive infrastructure — sync engines are being re-sold as state layers for agents and AI-generated apps rather than as offline-first tooling.
