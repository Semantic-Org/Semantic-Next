# Internationalization

## Goal

Build i18n into the framework as a first-class primitive — locale-aware formatting, UI string interpolation, RTL/LTR direction, language switching — not bolted on later.

The framing: making i18n "just work" out of the box dramatically expands the audience. Global-scale customers (Fortune 500, banks, healthcare, gov) treat i18n as table stakes; frameworks that punt it to userland lose this audience. Frameworks that bake it in cleanly — the way SUI bakes in event binding's `global` / `deep` / `outside` modifiers, surprising and simplifying — become differentiated.

This plan lands before Phase 4 component authoring because every primitive inherits the i18n contract. Generating 60+ components against an i18n-naive contract and retrofitting later means breaking changes across the whole library.

## Design / Implementation

*Initial scope — needs a pair session.* Open design surface:

- **Locale propagation.** Document attribute (`<html lang>`)? Settings inheritance? Signal at the root that descendants subscribe to? How does a sub-tree override locale (e.g. a footer rendered in a different language)?
- **String interpolation.** Template helper (`{t 'button.submit'}`)? Settings with locale-aware defaults? Slots for fully-translated content? Composition pattern across primitives that have built-in copy (modal close button, form validation errors, etc.)?
- **Formatters.** `formatNumber`, `formatRelativeTime`, `formatList`, `formatPlural`, `formatCurrency` joining the existing `formatDate`. Consistent locale-aware defaults.
- **RTL/LTR.** CSS logical properties by convention everywhere? Reactive direction primitive? Per-component direction overrides? How do flips of icons / arrows / progress bars get expressed?
- **Translation file format.** JSON? ICU MessageFormat? Custom? Does the framework ship a loader, or expose a hook for consumer-provided loading?
- **Language switching at runtime.** Re-render strategy — does flipping locale invalidate every translated expression? What's the perf story for swapping ~200 strings on a page?
- **Cross-framework parity (Phase 5 wrappers).** What does the i18n surface look like through React/Vue/Svelte wrappers? Idiomatic patterns differ — can wrappers translate the SUI primitive into each framework's conventional approach (e.g. `react-intl`, `vue-i18n`)?

## Open Questions

All design questions above. Pair session before scoping.

## Dependencies

None blocking. Lands before Phase 4 to avoid retrofitting components after the contract changes.

**Component Plugin Seam (Shipped in `#389` / `#390` / `#393`):**
`@semantic-ui/component` now provides `registerPlugin` and `addPlugin` (`packages/component/src/plugins/`), designed and tested directly against the i18n shape (`docs/src/examples/framework/plugins/component-plugins/i18n-plugin.js`):
- **`defineComponent` Option (`namespace: 'i18n'`, `appliesTo: 'all'`)**: Per-component namespace, locale, or messages override via `resolveSettings`, backed by `Plugin.createReactiveProxy` so mutating `settings.locale` at runtime wakes every reactive consumer across components and subtemplates.
- **`templateData` (`#393`)**: `locale: () => settings.locale`, `dir: () => settings.dir` — zero-argument functions in `templateData` are evaluated inside each template expression's `Reaction` by `ExpressionEvaluator`, enabling `{locale}`, `{#if is locale 'en'}`, and `dir={dir}` directly in template expressions without getters.
- **`templateHelpers`**: `t`, `formatNumber`, `formatCurrency`, `formatRelativeTime` (1+ arg helpers).
- **`lifecycleParams`**: `t`, `locale`, `setLocale` injected into component lifecycle and event callbacks.
