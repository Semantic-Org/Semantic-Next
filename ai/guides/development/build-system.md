## Mental Model: Two-System Architecture

**CRITICAL INSIGHT**: Semantic UI's build system serves two fundamentally different purposes:

### System 1: Pure JavaScript Libraries (`packages/`)

**What they are:**
- `@semantic-ui/reactivity` - Signals-based state management
- `@semantic-ui/query` - DOM querying utilities
- `@semantic-ui/templating` - Template compiler
- `@semantic-ui/utils` - Helper functions
- `@semantic-ui/renderer` - Lit HTML integration
- `@semantic-ui/component` - Component framework API (defineComponent)
- `@semantic-ui/specs` - Spec reader/validator

**Key characteristics:**
- Pure JavaScript code (no CSS, no web components)
- Can be used **standalone** in any framework (Vue, React, vanilla JS)
- Framework-agnostic utilities
- Standard library distribution pattern

**Build outputs:**
```
src/index.js              # Source (for bundlers)
dist/bundle/index.min.js  # Fully bundled (browser)
dist/cdn/index.min.js     # CDN-ized imports
```

---

### System 2: Web Component Framework (`@semantic-ui/core`)

**What it is:**
- **Actual UI components** (`<ui-button>`, `<ui-card>`, etc.)
- Custom elements registered with the browser
- Shadow DOM encapsulation
- CSS that must be inlined into components
- Component specs that define APIs
- Built **on top of** the packages

**Key characteristics:**
- Depends on all `@semantic-ui/*` packages
- Contains CSS files that need bundling
- Contains component specs (JSON → JS conversion)
- Must ship CSS inlined in component code (Shadow DOM requirement)
- Complex multi-stage build process

**Build outputs:**
```
dist/semantic-ui.js              # Full framework
dist/cdn/semantic-ui.min.js      # CDN version
dist/button/index.js             # Individual component

# Internal build artifacts (generated by build-ui-deps)
src/primitives/button/css/button-bundle.css      # Flattened CSS
src/primitives/button/specs/button-component.js  # Generated spec
```

---

### Dependency Direction

```
Application
    ↓ uses
@semantic-ui/core (web components)
    ↓ depends on
@semantic-ui/component (defineComponent API)
@semantic-ui/reactivity (Signal, Reaction)
@semantic-ui/templating (Template compiler)
@semantic-ui/query ($, $$)
@semantic-ui/renderer (Lit HTML)
@semantic-ui/utils (helpers)
@semantic-ui/specs (SpecReader)
    ↓ can be used standalone
Your Application / Other Frameworks
```

**Critical insight:**
- Packages are independent libraries
- Core is the web component framework built on those libraries
- You can use packages WITHOUT core
- Core MUST use the packages

## Build Scripts Deep Dive

All build scripts located in: `internal-packages/scripts/src/`

### 1. build-ui-framework.js

**Purpose**: Exports entire framework as single bundle

**What it builds**:
- Framework JS (all components + packages aggregated)
- Framework CSS (all styles aggregated)

**Output formats**: ESM, Bundle, CDN × (JS, CSS)

**Entry points**:
```javascript
// JavaScript
entryPoints: ['src/index.js']
entryNames: 'semantic-ui'

// CSS
entryPoints: ['src/css/all.css']
entryNames: 'semantic-ui'
```

**Output locations**:
```
dist/semantic-ui.js               # ESM unminified
dist/semantic-ui.min.js           # ESM minified
dist/semantic-ui.css              # CSS unminified
dist/semantic-ui.min.css          # CSS minified

dist/bundle/semantic-ui.js        # Bundle unminified
dist/bundle/semantic-ui.min.js    # Bundle minified
dist/bundle/semantic-ui.css       # Bundle CSS
dist/bundle/semantic-ui.min.css   # Bundle CSS minified

dist/cdn/semantic-ui.js           # CDN unminified
dist/cdn/semantic-ui.min.js       # CDN minified
dist/cdn/semantic-ui.css          # CDN CSS
dist/cdn/semantic-ui.min.css      # CDN CSS minified
```

**Options**:
```javascript
{
  watch: false,
  includeESM: true,
  includeCDN: true,
  includeBundle: true
}
```

### 2. build-ui-components.js

**Purpose**: Export each component as standalone file

**What it builds**:
- Individual primitives (`button`, `card`, `input`, etc.)
- Individual components (`mobile-menu`, `nav-menu`, etc.)
- Individual behaviors (`transition`, etc.)

**Entry patterns**:
```javascript
// Primitives
entryPoints: ['./src/primitives/**/index.js']
entryNames: '[dir]'  // Output: button.js, card.js, etc.
outbase: 'src/primitives'
filterEntries: (path) => !path.endsWith('src/primitives/index.js')

// Components
entryPoints: ['./src/components/**/index.js']
entryNames: '[dir]'  // Output: mobile-menu.js, nav-menu.js, etc.
outbase: 'src/components'

// Behaviors
entryPoints: ['./src/behaviors/**/index.js']
entryNames: '[dir]'  // Output: transition.js, etc.
outbase: 'src/behaviors'
```

**Output locations**:
```
dist/button/index.js              # ESM
dist/bundle/button.min.js         # Bundle
dist/cdn/button.min.js            # CDN

dist/card/index.js
dist/bundle/card.min.js
dist/cdn/card.min.js
# ... etc for all primitives/components/behaviors
```

**Why the filterEntries?**
- Prevents building the root `index.js` that aggregates all primitives
- Only builds individual component entry points

### 3. build-ui-deps.js ⚠️ CRITICAL

**Purpose**: Generate internal build dependencies for web components

**This is the most important script to understand** - it prepares web components for consumption.

**What it does:**

#### A. CSS Bundling

**The Problem:**
```javascript
// In ui-button component
import styles from './css/button.css';  // esbuild loader: { '.css': 'text' }
```

If `button.css` contains:
```css
@import './base.css';
@import './variants.css';

.button { /* ... */ }
```

The `@import` statements are **NOT followed** when CSS is loaded as text - they're just literal strings. The component receives broken CSS.

**The Solution:**
```javascript
// Pre-bundle CSS with esbuild's CSS loader
build({
  type: 'css',
  bundle: true,              // Follows @imports!
  entryPoints: ['src/primitives/**/css/*.css'],
  entryNames: '[dir]/../[name]-bundle',
  outbase: 'src',
  outdir: 'src',             // Output back to src/
  banner: { css: INTERNAL_CSS_BANNER }
})
```

**Output**: `src/primitives/button/css/button-bundle.css` (all @imports inlined)

**Component now imports**:
```javascript
import styles from './css/button-bundle.css';  // No @imports!
```

#### B. Spec JSON → JS Conversion

**The Problem:**
- Different environments have inconsistent JSON import support
- Node.js requires `assert { type: 'json' }`
- Some bundlers don't support JSON imports
- TypeScript requires `resolveJsonModule: true`

**The Solution:**
```javascript
// Convert JSON to JS modules
// Input: button.json
{
  "tagName": "ui-button",
  "variants": ["primary", "secondary"]
}

// Output: button.js
export default {
  "tagName": "ui-button",
  "variants": ["primary", "secondary"]
};
```

Now every environment can import it:
```javascript
import spec from './button.js';  // Works everywhere!
```

#### C. Component Spec Generation

**The SpecReader processes raw specs into web component specs:**

```javascript
const generateComponentSpecJS = async (spec, plural = false) => {
  const reader = new SpecReader(spec, { plural });
  const componentSpec = reader.getWebComponentSpec();

  return `// Auto-generated from ${spec?.tagName}.json
export default ${JSON.stringify(componentSpec, null, 2)};
`;
};
```

**Flow:**
```
button.json (raw spec)
    ↓ SpecReader.getWebComponentSpec()
button-component.js (processed web component spec)
    ↓ import in component
Component code
```

**Plural variants:**
```javascript
if (spec?.supportsPlural) {
  // Generates both:
  // - button-component.js (for <ui-button>)
  // - buttons-component.js (for <ui-buttons>)
}
```

#### D. Watch Mode for Specs

```javascript
if (watch) {
  // esbuild watches JSON files
  // On change, regenerates JS exports
  specWatcher = build({
    watch,
    write: false,           // Don't write esbuild output
    logLevel: 'silent',     // Just watch for changes
    entryPoints: specFiles,
    plugins: [
      callbackPlugin({
        onComplete: async (result, { isRebuild }) => {
          if (isRebuild) {
            await createComponentSpecs();
            await generateJSExportsFromSpecs();
          }
        },
      }),
    ],
  });
}
```

**Returns**: Array of build promises (CSS bundle, spec generation, spec watcher)

### 4. build-specs.js

**Purpose**: Export spec files to dist/ for package consumption

**What it builds**:
```javascript
entryPoints: [
  './src/specs/specs.js',
  './src/specs/component-specs.js'
]
```

**Output**: `dist/specs.js`, `dist/component-specs.js`

**Why ESM only?**
- Specs are just JSON data exports
- No need for bundled/CDN versions
- Consumers import for build-time usage

### 5. build-esm.js / build-bundle.js / build-cdn.js

**Three distribution formats** used by higher-level scripts:

#### build-esm.js

**Purpose**: ESM with externalized dependencies

```javascript
{
  format: 'esm',
  bundle: true,
  external: Object.keys(dependencies + peerDependencies),
  minify: false  // Also builds minified version
}
```

**Output**: `dist/[name].js`, `dist/[name].min.js`

**When used**:
- Modern bundlers (Vite, Webpack, Rollup)
- Node.js ESM imports
- Dependencies resolved by consumer

**For packages**: Not used in exports (source is used instead)
**For core**: Used for framework aggregation

#### build-bundle.js

**Purpose**: Fully bundled (all dependencies included)

```javascript
{
  bundle: true,
  minify: false  // Also builds minified version
}
```

**Output**: `dist/bundle/[name].js`, `dist/bundle/[name].min.js`

**When used**:
- Direct browser usage via `<script type="module">`
- Self-contained, no external dependencies
- Custom tooling

#### build-cdn.js

**Purpose**: CDN-ready with URL rewriting

```javascript
{
  cdn: true,     // Triggers resolveBareImports plugin
  bundle: true,
  minify: false  // Also builds minified version
}
```

**Output**: `dist/cdn/[name].js`, `dist/cdn/[name].min.js`

**What happens**:
```javascript
// Input code
import { Signal } from '@semantic-ui/reactivity';

// Output code (bare imports → CDN URLs)
import { Signal } from 'https://cdn.jsdelivr.net/npm/@semantic-ui/reactivity@0.17.0/dist/cdn/index.min.js';
```

**When used**:
- Direct browser usage with import maps
- No build step required
- All dependencies fetched from CDN

### 8. Core Build Library (lib/build.js)

**Main export**: `build()` function - wrapper around esbuild

**Key parameters**:
```javascript
{
  // Type
  type: 'javascript' | 'css',

  // Distribution format
  cdn: false,      // Enable CDN URL rewriting
  esm: false,      // ESM with external deps
  bundle: false,   // Bundle all deps

  // Output options
  minify: false,
  sourcemap: true,
  watch: false,

  // Entry/output
  entryPoints: [],
  outdir: '',
  outfile: '',
  filterEntries: null,  // Filter function for globs

  // Plugins
  plugins: [],
  onLoad: null,
  onComplete: null,

  // Auto-configuration
  readEntrypoints: true,  // From package.json
  addBanner: true,        // License banner
  addLog: true,           // Build logging
  packageFile: null       // Package.json (auto-loaded)

```

**Auto-configuration features**:

1. **Reads package.json**:
   - Auto-generates license banner
   - Auto-discovers entry points
   - Auto-determines output filenames
   - Externalizes dependencies for ESM builds

2. **Adds plugins automatically**:
   - `logPlugin` - Pretty console output
   - `resolveBareImports` - CDN URL rewriting
   - `callbackPlugin` - Lifecycle hooks

3. **Config constants** (lib/config.js):
```javascript
JS_BUILD_CONFIG = {
  target: ['chrome80', 'edge80', 'firefox78', 'safari14', 'ios14', 'opera67'],
  platform: 'browser',
  format: 'esm',
  loader: {
    '.ts': 'ts',
    '.html': 'text',
    '.css': 'text',   // Important for web components!
    '.wasm': 'file',
    '.png': 'file',
    '.svg': 'file'
  }
}

CSS_BUILD_CONFIG = {
  target: [...],
  loader: {
    '.css': 'css',    // CSS mode follows @imports
    '.svg': 'dataurl', // Inline SVGs
    '.png': 'file'
  }
}

CDN_CONFIG = {
  cdnRoot: 'https://cdn.jsdelivr.net/npm',
  cacheDir: '.cache',
  logging: 'silent'
}
```

### 3. esbuild-resolve-bare-imports

**Location**: `internal-packages/esbuild-resolve-bare-imports/src/index.js`

**Purpose**: Rewrite bare module imports to CDN URLs

**This is the most complex plugin** - enables CDN builds.

**Usage**:
```javascript
plugins: [
  resolveBareImports({
    packageJson: packageFile,
    cdnRoot: 'https://cdn.jsdelivr.net/npm',
    cacheDir: '.cache',
    logging: 'silent',
    directReplacements: {}
  })
]
```

**What it does**:

1. **Fetches entrypoints from jsDelivr API**:
   ```javascript
   // Query: https://data.jsdelivr.com/v1/packages/npm/@semantic-ui/reactivity@0.17.0/entrypoints
   // Response: { entrypoints: { js: { file: "dist/bundle/index.min.js" } } }
   ```

2. **Caches results**:
   ```
   .cache/@semantic-ui_reactivity@0.17.0.json
   ```

3. **Rewrites imports**:
   ```javascript
   // Input
   import { Signal } from '@semantic-ui/reactivity';

   // Output
   import { Signal } from 'https://cdn.jsdelivr.net/npm/@semantic-ui/reactivity@0.17.0/dist/bundle/index.min.js';
   ```

4. **Handles subpaths**:
   ```javascript
   // Input
   import transition from '@semantic-ui/query/plugins/transition';

   // Output
   import transition from 'https://cdn.jsdelivr.net/npm/@semantic-ui/query@0.17.0/plugins/transition';
   ```

5. **Supports direct replacements**:
   ```javascript
   directReplacements: {
     'lit': 'https://cdn.jsdelivr.net/npm/lit@3.0.0/index.js'
   }
   ```

**Logging levels**: `silent`, `minimal`, `normal`, `verbose`

## Export Conditions Strategy

**Export conditions map build outputs to use cases.**

Node.js resolves exports in condition order. First matching condition wins.

### Package Export Pattern (@semantic-ui/reactivity, etc.)

```json
{
  "exports": {
    ".": {
      "types": "./types/index.d.ts",
      "import": "./src/index.js",
      "browser": "./dist/bundle/index.min.js",
      "importmap": "./dist/cdn/index.min.js"
    }
  }
}
```

| Condition | Points To | Build | When Used |
|-----------|-----------|-------|-----------|
| `types` | `types/index.d.ts` | Manual types | TypeScript, IDEs |
| `import` | `src/index.js` | **Source** | Vite, Webpack, Rollup |
| `browser` | `dist/bundle/index.min.js` | build-bundle.js | Direct browser |
| `importmap` | `dist/cdn/index.min.js` | build-cdn.js | Import maps |

**Why source for `import`?**
- Enables tree-shaking
- Better source maps
- Faster bundler processing
- Pure JS libraries benefit from this

---

### Core Export Pattern (@semantic-ui/core)

**Framework import**:
```json
{
  "exports": {
    ".": {
      "types": "./types/index.d.ts",
      "import": "./dist/semantic-ui.js",
      "browser": "./dist/cdn/semantic-ui.min.js",
      "bundled": "./dist/semantic-ui.min.js",
      "default": "./dist/semantic-ui.js"
    }
  }
}
```

| Condition | Points To | Build | When Used |
|-----------|-----------|-------|-----------|
| `types` | `types/index.d.ts` | Manual types | TypeScript, IDEs |
| `import` | `dist/semantic-ui.js` | build-ui-framework (ESM) | Vite, Webpack |
| `browser` | `dist/cdn/semantic-ui.min.js` | build-ui-framework (CDN) | Direct browser |
| `bundled` | `dist/semantic-ui.min.js` | build-ui-framework (Bundle) | Custom tools |
| `default` | `dist/semantic-ui.js` | (same as import) | Fallback |

**Individual primitive import**:
```json
{
  "./button": {
    "import": "./src/primitives/button/index.js",
    "browser": "./dist/cdn/button.min.js",
    "bundled": "./dist/bundle/button.min.js",
    "default": "./src/primitives/button/index.js"
  }
}
```

**Why dist/ for framework but src/ for primitives?**

1. **Framework aggregation** (import `@semantic-ui/core`):
   - Pre-built reduces consumer build time
   - Large surface area (all components)
   - Still externalizes package dependencies

2. **Individual primitives** (import `@semantic-ui/core/button`):
   - Source enables tree-shaking
   - Consumer optimizes individual components
   - But source has generated dependencies (CSS bundles, specs)

---

### CSS Export Pattern

```json
{
  "./css": {
    "import": "./src/css/all.css",
    "default": "./src/css/all.css"
  }
}
```

**Why only import/default?**
- CSS doesn't have bare imports (no CDN rewriting needed)
- CSS processed by consumer's build pipeline
- No bundled/browser variants needed

**Always points to source** - consumers decide how to process.

---

### The Complete Export → Build Mapping

```
Consumer Intent          Export Condition    Build Script           Output
════════════════════════════════════════════════════════════════════════════

Modern bundler (Vite)  → "import"        → (source)             → src/index.js (packages)
                                                                   dist/semantic-ui.js (core)

Direct browser         → "browser"       → build-bundle.js      → dist/bundle/index.min.js (packages)
                                         → build-cdn.js         → dist/cdn/semantic-ui.min.js (core)

Import map             → "importmap"     → build-cdn.js         → dist/cdn/index.min.js (packages)

Custom tooling         → "bundled"       → build-bundle.js      → dist/semantic-ui.min.js (core only)

TypeScript             → "types"         → Manual types         → types/index.d.ts

Fallback/Unknown       → "default"       → (same as "import")
```

## Build Dependencies & Orchestration

**Wireit manages build dependencies** - ensures correct order and caching.

### Root Build Dependency Graph

```
build
├── build:packages (parallel)
│   ├── ./packages/component:build
│   ├── ./packages/query:build
│   ├── ./packages/reactivity:build
│   ├── ./packages/renderer:build
│   ├── ./packages/specs:build
│   ├── ./packages/tailwind:build
│   ├── ./packages/templating:build
│   └── ./packages/utils:build
├── build:ui-deps
├── build:ui-components
└── build:specs

build:ui
├── build:ui-deps
├── build:ui-components
└── build:specs

build:packages (runs 8 package builds in parallel)

watch (service: true - runs indefinitely)
└── (watches ui-deps, ui-framework)
```

### Package Build Dependencies

Each package:
```
build
├── build:esm
├── build:bundle
└── build:cdn
```

All run in parallel (no dependencies between them).

### Why Build Order Matters

**Critical sequence**:

1. **Packages first** (`build:packages`):
   ```javascript
   // Components import packages
   import { defineComponent } from '@semantic-ui/component';
   import { Signal } from '@semantic-ui/reactivity';
   ```
   Packages must exist before components can import them.

2. **UI deps second** (`build:ui-deps`):
   ```javascript
   // Components import generated files
   import styles from './css/button-bundle.css';     // Generated!
   import spec from './specs/button-component.js';   // Generated!
   ```
   Generated files must exist before components build.

3. **UI components third** (`build:ui-components`):
   ```javascript
   // Now button/index.js is complete
   // - Has package imports (from step 1)
   // - Has CSS bundles (from step 2)
   // - Has specs (from step 2)
   // Can be bundled!
   ```

4. **Framework fourth** (`build:ui-framework`):
   ```javascript
   // src/index.js imports all components
   // Components must be complete before framework aggregates them
   ```

**This order is enforced by wireit dependencies.**

### Watch Mode Coordination

```javascript
// watch.js
{
  watchDeps: true,       // Watches CSS/specs, regenerates
  watchFramework: true,  // Watches framework for playground
  watchComponents: false // Usually not needed in dev
}
```

**What happens during development**:

1. **Edit button.css**:
   ```
   button.css changes
       ↓
   build-ui-deps rebuilds button-bundle.css
       ↓
   build-ui-framework rebuilds semantic-ui.js (imports button)
       ↓
   Docs hot-reload
   ```

2. **Edit button.json spec**:
   ```
   button.json changes
       ↓
   build-ui-deps regenerates button-component.js
       ↓
   build-ui-framework rebuilds semantic-ui.js
       ↓
   Docs hot-reload
   ```

**Why watch framework but not components?**
- Docs playground uses `dist/semantic-ui.js` (framework build)
- Individual component builds not needed for dev
- Faster rebuild times

## Idiosyncrasies & Critical Details

### 1. CSS Import Flattening (Web Component Requirement)

**Why it happens**:
- Web components load CSS as **text** (esbuild loader: `{ '.css': 'text' }`)
- Text loader doesn't follow `@import` statements
- CSS arrives broken with literal `@import` strings

**Solution**:
- `build-ui-deps` pre-bundles CSS with CSS loader (follows `@import`)
- Outputs `-bundle.css` files
- Components import the bundle

**Banner warning**:
```css
/**
  ---DO NOT EDIT THIS FILE DIRECTLY---
  This CSS file was concatenated from files listed in the css/ folder as part of a build process
  This is to allow for js import with @import links which will not be followed
**/
```

**Impact**:
- Generated files committed to repo
- `build-ui-deps` MUST run before components build
- Even source consumption requires generated files

---

### 2. JSON → JS Conversion (Compatibility)

**Why it happens**:
- JSON imports inconsistent across environments:
  - Node.js: `import spec from './spec.json' assert { type: 'json' }`
  - Browsers: Often unsupported
  - Bundlers: Varies by tool
  - TypeScript: Requires `resolveJsonModule: true`

**Solution**:
- Convert all JSON to JS modules:
  ```javascript
  export default { /* JSON data */ };
  ```

**Impact**:
- All `.json` files get `.js` equivalents
- Both committed to repo
- Source code imports `.js` versions

---

### 3. Spec Generation (Web Component API)

**Why it happens**:
- Raw specs are authored as JSON
- Web components need processed specs (defaults, validation, etc.)
- SpecReader transforms raw → component spec

**Process**:
```
button.json (authored)
    ↓ SpecReader.getWebComponentSpec()
button-component.js (generated)
    ↓ import in component
Component uses processed spec
```

**Plural variants**:
```
button.json
    ↓ SpecReader with plural: false
button-component.js

button.json
    ↓ SpecReader with plural: true
buttons-component.js
```

**Impact**:
- Multiple generated files per spec
- Spec changes require rebuild
- Watch mode handles auto-regeneration

---

### 4. Generated Files in Repository

**What's committed**:
```
src/primitives/button/css/button-bundle.css     # Generated
src/primitives/button/specs/button.js           # Generated
src/primitives/button/specs/button-component.js # Generated
```

**Why commit generated files?**
- Consumers import from source via `"import"` condition
- Source must be immediately usable
- No build step required for package consumers

**Trade-offs**:
- ✅ Source works immediately
- ✅ No consumer build step
- ❌ Git diffs include generated files
- ❌ PR noise

**Alternative considered and rejected**:
- Don't commit generated files
- Require consumers run `postinstall` script
- Breaks "just npm install" workflow

---

### 5. Build Order Dependencies

**Critical sequences**:

```
Packages → UI Deps → UI Components → UI Framework
```

**Violated if**:
- Components build before packages → Import errors
- Components build before ui-deps → Missing CSS bundles, specs
- Framework builds before components → Incomplete aggregation

**Wireit enforces this** - don't bypass wireit for full builds.

---

### 6. Watch Mode Selectivity

**Default watch targets**:
- ✅ `build-ui-deps` (CSS, specs change frequently)
- ✅ `build-ui-framework` (playground needs this)
- ❌ `build-ui-components` (rarely needed)

**Why not watch components?**
- Slower (builds many individual files)
- Playground uses framework build, not component builds
- Can enable if needed: modify `watch.js`

---

### 7. ESM Builds Not in Package Exports

**Packages build ESM** (`dist/index.js`) but exports point to **source**:

```json
{
  "exports": {
    ".": {
      "import": "./src/index.js"  // Not dist/index.js!
    }
  }
}
```

**Why build ESM if not exported?**
- Historical artifact
- Potential future use
- Testing/verification
- Available for manual consumption

**Core uses ESM builds**:
```json
{
  "exports": {
    ".": {
      "import": "./dist/semantic-ui.js"  // Uses ESM dist
    }
  }
}
```

---

### 8. CSS Exports Always Point to Source

```json
{
  "./css": {
    "import": "./src/css/all.css"  // Source, not dist
  }
}
```

**Why?**
- CSS processed by consumer's pipeline
- No bundling/minification needed from Semantic UI
- Consumer decides: inline, extract, PostCSS, etc.

**Even though**:
- JS has multiple dist variants (ESM, Bundle, CDN)
- CSS keeps it simple

---

### 9. Target Browsers

```javascript
TARGET_BROWSERS = [
  'chrome80',
  'edge80',
  'firefox78',
  'safari14',
  'ios14',
  'opera67'
]
```

**Impact**:
- Modern browser features allowed
- No IE11 support
- ES2020+ features safe
- Native async/await, optional chaining, etc.

---

### 10. Service Mode for Watch

```json
{
  "wireit": {
    "watch": {
      "command": "node ./internal-packages/scripts/src/watch.js",
      "service": true  // Runs indefinitely
    }
  }
}
```

**Wireit service mode**:
- Doesn't exit
- Keeps watching
- Other tasks can depend on it
- Used by `dev` task

## Summary

**The build system serves two purposes**:
1. **Library distribution** (packages/) - Standard JS tooling
2. **Web component assembly** (core) - Complex multi-stage process

**Key build stages**:
1. Build packages (parallel)
2. Generate UI deps (CSS bundles, specs)
3. Build UI components (individual)
4. Build UI framework (aggregated)

**Critical scripts**:
- `build-ui-deps.js` - Prepares web components (MOST IMPORTANT)
- `build-ui-framework.js` - Aggregates framework
- `build-ui-components.js` - Individual component builds

**Distribution formats**:
- **ESM**: External deps, for bundlers
- **Bundle**: All deps included, for browsers
- **CDN**: URL-rewritten imports, for import maps

**Export conditions map builds to use cases** - understanding this mapping is key to understanding the build system.
