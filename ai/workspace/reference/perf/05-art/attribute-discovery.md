# ART: Attribute Discovery During Hydration — Framework Survey

How do modern frameworks tell the client which DOM attributes are dynamic after the server has already evaluated expressions inline?

This document surveys seven frameworks: Solid.js, Svelte 5, Qwik, Marko 6, Lit 3, Vue/Vapor, and Angular. For each, it examines the server encoding strategy, client discovery mechanism, and architectural tradeoffs. The final section synthesizes these into a taxonomy and draws implications for Semantic UI's `data-sui-bind` approach.

## Taxonomy of Approaches

Before the per-framework details, there are four fundamental strategies for encoding "which attributes are dynamic" into server output:

| Strategy | Description | Frameworks |
|---|---|---|
| **Compiled DOM paths** | Compiler emits hardcoded firstChild/nextSibling walks. Client replays the walk without scanning. | Marko 6, Svelte 5, Solid.js |
| **Runtime marker scanning** | Server embeds sentinel strings or comment nodes. Client uses TreeWalker/regex to find them. | Lit 3, (Semantic UI current) |
| **Full-graph serialization** | Server serializes the entire reactive graph (state, subscriptions, event handlers) into HTML attributes and `<script>` blocks. | Qwik |
| **View annotation metadata** | Server embeds a structured metadata blob (JSON) keyed to component/view indices. Client walks the view tree and applies bindings from metadata. | Angular |

Most frameworks combine strategies. Solid.js uses compiled paths for element access but markers for content boundaries. Svelte uses compiled paths for attribute bindings but comment markers for block boundaries.

The critical axis is **where the binding-to-element mapping lives**:

- **On the element** (self-describing): The element carries its own binding metadata. Discovery is local. Examples: Qwik's `on:click` attributes, Semantic UI's proposed `data-sui-bind`.
- **In the code** (compiler-derived): The compiled output contains hardcoded DOM navigation instructions. The server emits no explicit binding markers for attributes. Examples: Svelte, Solid, Marko.
- **In external metadata** (sidecar): A serialized data structure (in a `<script>` tag or annotation attribute) maps indices to DOM positions. Examples: Angular's `__nghData__`, Qwik's `<script type="qwik/json">`.

## Solid.js

### Architecture: Compiled DOM Paths + Hydration Keys

Solid's compiler produces two outputs for each component: a CSR (client-side rendering) function and an SSR function. The SSR function is pure string concatenation using template literals. The CSR function contains hardcoded DOM traversal paths.

### Server Encoding

The SSR compiler output looks like:

```js
// Server-compiled output (simplified)
const _tmpl$ = [
  '<div class="', '" data-hk="', '"><span>', '</span></div>'
];

function MyComponent(props) {
  return ssr(_tmpl$, escape(props.class), ssrHydrationKey(), escape(props.name));
}
```

Key encoding mechanisms:
- **`data-hk` attributes**: Every hydration-relevant element gets a `data-hk="0-0-0"` attribute. The value is a hierarchical context ID (`component-child-sibling`) generated by `ssrHydrationKey()`.
- **Comment markers**: `<!--#-->` and `<!--/-->` delimit component boundaries and dynamic content regions.
- **No attribute-level markers**: Dynamic attribute values are evaluated inline on the server. `class="dark"` appears as a plain attribute in the HTML. The server does NOT mark which attributes are dynamic.

### Client Discovery

The client does NOT scan the DOM for dynamic attributes. Instead:

1. `hydrate()` sets `sharedConfig.context` and populates a registry.
2. The compiled client code calls `getNextElement()`, which looks up the element by hydration key from `sharedConfig.registry` rather than cloning a template.
3. The compiled code then runs the same reactive setup it would during CSR — `createEffect(() => el.className = props.class)` — but against the existing DOM element instead of a freshly cloned one.

The binding-to-element mapping is entirely in the compiled code. The compiler knows "the third `firstChild.nextSibling` in this template has a dynamic `class` attribute" at build time. The `data-hk` attribute exists only for element identity (finding the right DOM node), not for describing what bindings exist.

### Attribute Discovery Specifically

**Attributes are not "discovered" at all.** The compiled client code already knows which attributes are dynamic because it compiled the same source. The only information the server provides is "which DOM node is this component's root" (via `data-hk`). From there, the compiled code navigates to specific children using hardcoded paths.

This means:
- Zero runtime scanning cost for attribute discovery.
- The server and client must be compiled from the same source (version coupling).
- No ability to hydrate server output from a different build.

- [SSR Specification (Issue #109)](https://github.com/solidjs/solid/issues/109) — foundational design discussion
- [Hydration bug with Dynamic (Issue #2384)](https://github.com/solidjs/solid/issues/2384) — shows how compiled paths break with dynamic component types

## Svelte 5

### Architecture: Compiled DOM Paths + Comment Boundary Markers

Svelte 5 compiles components into two separate outputs: `generate: "client"` and `generate: "server"`. The client output contains imperative DOM creation/update code. The server output is string concatenation.

### Server Encoding

Svelte 5 uses two types of markers in server output:

1. **`<!--[-->` / `<!--]-->` comment pairs**: Block boundary markers around components, `{#if}` blocks, `{#each}` blocks, and dynamic content regions. These prevent text node merging and delineate component boundaries.

2. **`data-svelte-h` attribute**: A hash attribute placed on elements that contain only static content. During hydration, elements with a matching `data-svelte-h` hash are skipped entirely — no reactive wiring needed. This is an optimization: rather than marking what IS dynamic, Svelte marks what is NOT dynamic.

**Dynamic attributes are NOT explicitly marked in the server output.** Like Solid, Svelte relies on the compiled client code knowing which attributes are dynamic.

### Client Discovery

The hydration walk in Svelte 5 uses `hydrate_node` as a cursor that advances through the DOM:

1. The compiled client code calls internal functions like `$.first_child(node)`, `$.sibling(node)`, and `$.child(node)` to navigate.
2. For elements with `data-svelte-h`, the entire subtree is skipped.
3. For dynamic elements, the compiled code calls `$.set_attribute(element, 'class', value)` or `$.attr_effect(element, () => value)` directly against the hydration cursor's current position.

The client code has a single-pass hydration strategy (introduced in [PR #11770](https://github.com/sveltejs/svelte/pull/11770)) that walks the DOM once, advancing the cursor as the compiled code accesses nodes. This avoids the two-pass approach of earlier Svelte versions.

### Attribute Discovery Specifically

Like Solid, **attributes are not discovered at runtime.** The compiled client code contains explicit instructions like:

```js
// Simplified compiled output
let div = $.first_child(fragment);  // navigate to the div
$.attr_effect(div, () => `class-${state}`);  // wire reactive attribute
```

The compiler knew at build time that this div has a dynamic `class` attribute. The server output contains no metadata about this fact. The client code simply navigates to the correct element and wires the binding.

### Size Impact of Markers

The comment markers (`<!--[-->` / `<!--]-->`) add measurable overhead. [Issue #14099](https://github.com/sveltejs/svelte/issues/14099) reports that Svelte 5's SSR output is ~18% larger than Svelte 4's due to these markers. [Issue #15200](https://github.com/sveltejs/svelte/issues/15200) reports excessive marker insertion in some cases.

## Qwik

### Architecture: Full Resumability via DOM-Serialized Reactive Graph

Qwik takes the most radical approach: it serializes the entire application state, reactive subscriptions, and event handler references directly into the HTML. There is no hydration — the client "resumes" execution from the serialized state.

### Server Encoding

Qwik embeds three types of information in the server output:

1. **Event handler attributes (`on:click`, `on:input`, etc.)**: QRL (Qwik Resource Locator) strings that encode the module path, export name, and captured closure variable indices.
   ```html
   <button on:click="./chunk-a.js#Counter_onClick[0]" q:id="3">
     Count: 7
   </button>
   ```

2. **`q:id` attributes**: Unique node identifiers that allow the serialized state to reference DOM nodes.

3. **`<script type="qwik/json">` block**: A JSON blob containing the full reactive graph:
   - Object references (state, props, context)
   - Subscription mappings (which signals are watched by which effects)
   - Captured closure variables indexed by `q:id`

### Client Discovery

Qwik does NOT discover dynamic attributes. Instead:

1. The **Qwikloader** (a ~1KB inline script) listens for global events and lazily loads the appropriate handler module when an event fires.
2. When a handler is loaded, it deserializes its captured variables from the `<script type="qwik/json">` block using the `q:id` references.
3. Reactive bindings are restored lazily — only when a signal is written to does Qwik walk the subscription graph and update the relevant DOM nodes.

The entire reactive graph is serialized, so the client knows exactly which attributes are dynamic and which signals they depend on — but this information is resolved lazily rather than eagerly during a hydration pass.

### Qwik 2.0 Changes

Qwik 2.0 introduces significant improvements:
- **Comment node removal**: v2 eliminates comment markers, using `document.createTreeWalker` with depth-first sequence numbers instead of explicit `q:id` attributes on every node.
- **Lighter serialization**: Loaders are not serialized by default. `useSerializer$` is required for server-to-client data transfer.
- **Smaller HTML output**: Removing comments and default serialization produces significantly lighter HTML.

Source: [Towards Qwik 2.0](https://www.builder.io/blog/qwik-2-coming-soon)

### Attribute Discovery Specifically

Attributes are not "discovered" because the subscription graph in the JSON blob already says "signal X is bound to attribute Y on node with q:id Z." This is the most explicit encoding of any framework — it's effectively a database of all reactive bindings serialized into the HTML.

The tradeoff: HTML payload size. The `<script type="qwik/json">` block can be significant for large applications. Qwik 2.0 mitigates this by moving serialized data to the end of the HTML stream and making serialization opt-in.

### Relevant Issues / RFCs

- [Towards Qwik 2.0 blog post](https://www.builder.io/blog/qwik-2-coming-soon) — elimination of comment nodes and lighter serialization
- [Resumability Without Serialization (HackMD)](https://hackmd.io/@0u1u3zEAQAO0iYWVAStEvw/Hyu_IZQq2) — theoretical exploration of minimal serialization

## Marko 6

### Architecture: Compiler-Split Components + Encoded DOM Walks

Marko 6 takes the most aggressive compilation approach. The compiler splits each component into multiple independently loadable pieces along the reactive dependency graph. Only components with browser-side state or event handlers are sent to the client at all.

### Server Encoding

Marko's server rendering:

1. **Marks component boundaries** in HTML using comment pairs or inline `<script>` registration tags.
2. **Serializes scope data** — only the leaf nodes of the reactive graph that the client actually needs (signals read from DOM, event handlers, effects). The compiler traces dependencies cross-file and determines the minimal serialization set.
3. **Does NOT mark dynamic attributes** in the HTML. Like Solid and Svelte, the compiled code knows which attributes are dynamic.

### Client Discovery: Encoded Walks

This is Marko 6's most distinctive feature. The compiler emits "encoded walks" — compressed sequences of `firstChild` and `nextSibling` operations that navigate from a known root to every reactive DOM node.

For example, a walk encoded as `"DNAS"` might mean:
- `D` (down) = `firstChild`
- `N` (next) = `nextSibling`
- `A` (attr) = bind attribute at current position
- `S` (skip) = advance past static content

The client decodes the walk string and navigates the real DOM tree, finding each dynamic node without scanning or matching. This is extremely memory-efficient — no element references need to be stored beyond the walk string itself.

### Partial Hydration

Marko's partial hydration is automatic at the sub-template level. The compiler determines which components have browser-side behavior and only sends those to the client. A page with 100 components where only 3 have event handlers ships only those 3 components' code and scope data.

This means the attribute discovery question is often moot — if a component has no browser behavior, it's not hydrated at all, and its attributes are never re-examined.

## Lit 3

### Architecture: Runtime Marker Scanning with Tagged Template Literals

Lit is the closest analog to Semantic UI's current approach. It uses a runtime marker-based system rather than compiled DOM paths.

### Server Encoding

Lit SSR emits rich markers in the HTML:

1. **`<!--lit-part HASH-->` / `<!--/lit-part-->` comments**: Delimit template instances. The hash is derived from the template's static strings, allowing the client to match server output with the correct template.

2. **`<!--lit-node N-->` comments**: Placed before elements that have bindings. `N` is the node index within the template part. This tells hydration "the next element has bindings at part index N."

3. **`$lit$` attribute suffix**: During template preparation (not SSR specifically), bound attribute names are suffixed with `$lit$` (e.g., `class$lit$="value"`). This prevents browsers from applying partial attribute parsing (important for `style` in IE/Edge and SVG attributes). During SSR, the actual evaluated attribute values are written, but the part structure is encoded in the comments.

4. **`<?lit$RAND$>` processing instructions**: Used as text node markers (parsed as comment nodes by the browser), with a random suffix for collision avoidance.

### Client Discovery

Lit's hydration (via `@lit-labs/ssr-client`) walks the server-rendered DOM and reconciles it with the template's part structure:

1. Find `<!--lit-part HASH-->` comments to identify template instances.
2. Match the hash against registered templates to get the part list (which parts are ChildParts, AttributeParts, PropertyParts, EventParts, BooleanAttributeParts).
3. Walk forward from each `<!--lit-node N-->` to find the associated element.
4. Re-create the Part objects and connect them to the existing DOM nodes.
5. Event listeners are freshly attached (they can't be serialized).

The critical insight: Lit's hydration uses the **template identity** (hash of static strings) to know what bindings exist. The comment markers provide DOM navigation waypoints. The actual attribute names and binding types come from the template's part list, not from the DOM.

### Attribute Discovery Specifically

Lit does NOT encode which specific attributes are dynamic in the server HTML. The `<!--lit-node 0-->` comment says "this element has bindings" but doesn't say which attributes. The client reconstructs this from the template's compiled part list (derived from the tagged template literal's static strings at registration time).

This design works because Lit's templates are defined as tagged template literals with fixed static strings:
```js
html`<div class=${expr1} id=${expr2}>...</div>`
```
The static strings `['<div class=', ' id=', '>...</div>']` are the template identity. The positions between static strings are the bindings. The client has this information from the template definition, not from the server output.

## Vue / Vapor Mode

### Architecture: Compiled Imperative DOM Code (Vapor) / VDOM Diffing (Classic)

Vue has two rendering modes with different hydration strategies:

**Classic Vue 3 (VDOM):** Uses virtual DOM reconciliation during hydration. The client creates the vnode tree, then "adopts" existing DOM nodes instead of creating new ones. Attribute bindings are in the vnode tree from the compiled render function.

**Vue Vapor (upcoming, expected stable in Vue 3.6):** Compiles templates directly to imperative DOM operations, bypassing the virtual DOM entirely.

### Server Encoding (Classic Vue)

Vue 3 SSR output contains:
- `data-server-rendered="true"` on the root element (hydration trigger).
- No attribute-level binding markers. Dynamic attribute values are evaluated inline.
- Comment markers for teleports, suspense boundaries, and async components.

### Server Encoding (Vapor)

Vue Vapor's SSR strategy is **still under development** as of early 2026. The existing Vue SSR output format does not include attribute-level markers. Vapor's compiler produces imperative code like:

```js
// Simplified Vapor compiled output
const n0 = template('<div class=""><span></span></div>');
const el0 = n0.firstChild;
renderEffect(() => {
  setAttr(el0, 'class', ctx.className);
});
```

The client code navigates via compiled paths (`firstChild`, `nextSibling`) from a template root, identical to the Solid/Svelte approach. No runtime attribute scanning.

### Client Discovery

For both modes, attribute discovery is compiler-derived:
- The compiled render function knows which attributes are dynamic.
- The client navigates to the correct DOM node and applies bindings directly.
- The server output does not encode this information.

### Vapor Hydration Status

As of early 2026, Vapor's SSR hydration support is listed as "not yet fully supported" in the official docs. The Vapor compiler currently generates client-side code. Server rendering and the hydration bridge are active areas of development.

## Angular

### Architecture: View Annotation Metadata + Compiled Template Instructions

Angular uses a hybrid approach: compiled template instructions for binding knowledge combined with serialized view metadata for DOM structure navigation.

### Server Encoding

Angular SSR (with hydration enabled since Angular 16+) embeds:

1. **`ngh` attribute**: Placed on component host elements. The value is an index into the `__nghData__` array.
   ```html
   <app-header ngh="0">...</app-header>
   ```

2. **`ngb` attribute**: Placed on defer block boundaries.
   ```html
   <div ngb="d0">...</div>
   ```

3. **`<script id="ng-state" type="application/json">` block**: Contains the `__nghData__` and `__nghDeferData__` objects. These encode the view tree structure:

   ```json
   {
     "__nghData__": [{
       "c": { "0": { "i": "comp-1", "r": 2 } },
       "t": { "0": "t100", "1": "t200" }
     }]
   }
   ```

   Fields:
   - `c` — child component map (index to component config)
   - `t` — template reference map (index to template ID)
   - `r` — root node count (number of top-level DOM nodes in a view)
   - `i` — component type identifier

4. **No per-attribute markers**: Dynamic attribute values are evaluated inline. The serialized metadata encodes the view/component tree structure, not individual attribute bindings.

### Client Discovery

Angular's hydration process:

1. Read `__nghData__` from the serialized `<script>` block.
2. Walk the component tree. For each component with an `ngh` attribute, look up its view annotation.
3. The annotation tells Angular how many root nodes the view has and where child components are positioned.
4. The compiled template instructions (from the component's `@Component` decorator compilation) contain the actual binding information — which attributes, properties, and event listeners exist.
5. Angular replays the template instructions against the existing DOM, connecting bindings without recreating elements.

Event replay: Events that fire before hydration completes are captured and replayed after the component is hydrated. This is built into Angular's event dispatch system.

### Incremental Hydration

Angular 19+ supports incremental hydration with `@defer` blocks:
- The server renders the full content inside defer blocks.
- The client keeps it in a "dehydrated" state (static HTML shell) until a trigger fires.
- Triggers: `hydrate on idle`, `hydrate on viewport`, `hydrate on interaction`, `hydrate on hover`, `hydrate never`.
- When triggered, Angular loads the component code and hydrates just that section.

This is relevant to attribute discovery because it means Angular must track which sections of the DOM are dehydrated and associate them with their component code for lazy loading.

## Comparative Analysis

### How Each Framework Answers "Which Attributes Are Dynamic?"

| Framework | Server Marks Attributes? | Client Discovery Method | Encoding Location |
|---|---|---|---|
| **Solid.js** | No | Compiled code has hardcoded DOM paths | In the compiled output (code) |
| **Svelte 5** | No (marks static with `data-svelte-h`) | Compiled code has cursor-based navigation | In the compiled output (code) |
| **Qwik** | Yes (full reactive graph) | Deserializes subscription graph from JSON | `<script type="qwik/json">` + `q:id` attrs |
| **Marko 6** | No | Encoded walk strings + compiled splits | In the compiled output (code) |
| **Lit 3** | Partially (comment waypoints) | Template hash lookup + part list from registration | Comment markers + code-side template |
| **Vue Vapor** | No | Compiled imperative DOM code | In the compiled output (code) |
| **Angular** | No (marks view structure) | View annotations + compiled template instructions | `<script>` metadata + `ngh` attrs + code |

### Key Observations

**1. Most frameworks don't mark dynamic attributes at all.**

Five of seven frameworks (Solid, Svelte, Marko, Vue Vapor, Angular) rely entirely on compiled code to know which attributes are dynamic. The server evaluates expressions inline and the client uses the same compiled template to re-navigate to the correct DOM positions. This works because both sides are compiled from the same source at build time.

**2. The "compiled paths" approach dominates.**

The `firstChild`/`nextSibling` navigation pattern — where the compiler emits a fixed sequence of DOM traversal operations — is the most common strategy. Solid, Svelte, Marko, and Vue Vapor all use this pattern. Marko takes it furthest with encoded walk strings that compress the path into a compact format.

**3. Runtime scanning is rare and considered expensive.**

Only Lit uses something resembling runtime scanning (finding `<!--lit-node-->` comments). Even Lit minimizes this by using template identity hashes to narrow the search. The general consensus across frameworks is that runtime DOM scanning is slower than compiled navigation.

**4. Self-describing elements are the exception, not the rule.**

Only Qwik places per-element metadata (event handler QRLs) on the elements themselves. And even Qwik is moving away from this in v2, preferring TreeWalker-based depth-first numbering over explicit `q:id` attributes.

**5. The "compiled from same source" assumption doesn't hold for web components.**

This is the crucial distinction for Semantic UI. Solid, Svelte, Marko, and Vue all assume the client and server are compiled from the same source in the same build. The compiled code has identical knowledge of the template structure. This assumption fails for web components consumed via CDN, where:
- The server might render with a different version than the client loads.
- The component definition might not be available at server render time.
- Third-party consumers can't recompile the component.

### Tradeoff Matrix

| Dimension | Compiled Paths | Runtime Scanning | Self-Describing | View Metadata |
|---|---|---|---|---|
| **HTML overhead** | None | Comment nodes | Per-element attrs | Script block |
| **Discovery speed** | O(1) per binding | O(n) elements | O(1) per element | O(1) per component |
| **Version coupling** | Tight (same build) | Moderate (marker format) | Loose (attr format) | Tight (metadata format) |
| **Debug visibility** | None (in code) | Markers in DOM | Attrs in DevTools | JSON in page source |
| **Streaming compat** | Yes (path is static) | Needs full tree | Yes (local) | Needs metadata block |
| **Web Component compat** | Poor (requires compilation) | Good | Excellent | Moderate |

## Implications for Semantic UI

### Why Semantic UI Can't Use Compiled Paths

The compiled DOM path approach (Solid/Svelte/Marko/Vue) requires that the client code is compiled from the same template source as the server code. This is architecturally incompatible with Semantic UI's model:

1. **CDN distribution**: Components are consumed as pre-built packages. Users don't recompile them.
2. **Declarative Shadow DOM**: The server output must be self-contained HTML that any client version can hydrate.
3. **Version skew**: A component's server-rendered output might be hydrated by a newer or older client version.
4. **Dynamic template compilation**: Semantic UI compiles templates at runtime (via `TemplateCompiler`), not at build time. There is no pre-compiled client code with baked-in DOM paths.

### Why `data-sui-bind` Aligns With Best Practices

The `data-sui-bind` approach (from `attribute-discovery-arbitration.md`) is architecturally closest to Qwik's self-describing element strategy, but lighter:

| Feature | Qwik | Semantic UI `data-sui-bind` |
|---|---|---|
| What's encoded | Full reactive graph + handlers | Attribute name to entry ID mapping |
| Format | QRL strings + JSON blob | Simple `name:id` pairs |
| Scope | Entire application state | Per-element bindings only |
| Cleanup | Persistent (never removed) | Removed after hydration |
| Handler serialization | Yes (module paths) | No (events re-attached from template) |

The key advantage: `data-sui-bind` gives the client everything it needs to wire attribute bindings without knowing the template structure in advance. The entries array (from `buildHTMLString`) provides the expression metadata. The bind attribute provides the element-to-entry mapping. Together, they're sufficient for hydration without a reference DOM, compiled paths, or external metadata blocks.

### Lessons From the Survey

1. **Comment markers for block boundaries are universal.** Every framework uses comment nodes (or equivalent) to delimit dynamic content regions ({#if}, {#each}, components). Semantic UI's `<!--sui-block:v1:N-->` pattern is consistent with industry practice.

2. **Attribute-level markers are rare because most frameworks can avoid them.** But the frameworks that avoid them do so via tight compile-time coupling that Semantic UI doesn't have. In the absence of compiled paths, self-describing elements are the robust alternative.

3. **The Lit model is the closest precedent** for a runtime-compiled, web-component-native framework doing SSR. But Lit encodes less information in the DOM (just waypoint comments) and relies on template identity hashes. Semantic UI's approach of encoding the actual binding spec per element is more explicit and more robust against version skew.

4. **Angular's view metadata approach** is instructive for understanding how a framework without compiled DOM paths (Angular's Ivy compiler produces instructions, not paths) still avoids per-element attribute markers. Angular's compiled instructions + external metadata is a viable alternative to `data-sui-bind`, but it requires a metadata block and tight version coupling.

5. **Qwik 2.0's direction is notable**: moving from per-element IDs to TreeWalker-based depth-first numbering. This reduces HTML overhead at the cost of requiring the serialized graph to use positional rather than identity-based references. For Semantic UI, the opposite direction (explicit per-element binding attributes) is justified by the web component distribution model.

6. **Marko's encoded walks** are the most elegant solution for compiled frameworks, achieving minimal code size, minimal memory usage, and O(1) per-binding discovery. If Semantic UI ever adds an ahead-of-time compilation step, encoding walk strings into the compiled output would be worth investigating as a complement to the `data-sui-bind` approach.
